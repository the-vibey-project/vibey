* **`vibey-gh setup`, one idempotent command from a fresh clone to a working contributor environment:** it syncs the environment (`uv sync --extra dev`), installs the pre-commit framework's three hook types and then the provenance hooks in the order that works (the `core.hooksPath` rule CONTRIBUTING.md used to state in prose is now code: it lifts its own `.githooks` value for the install and puts it back, even if the install fails), checks that the test database can be reached and that its role can create databases, and ends by running `vibey doctor`. Each step reports what it observed afterwards (`done`, `unchanged`, `skipped`, `failed`, `unknown`, or `advisory`), not what it ran; a second run reports `unchanged` and changes nothing. It never overwrites a `core.hooksPath` it did not set (a global, system or other local value is named and left alone), and never creates a PostgreSQL role, password or `~/.pgpass`; when the database check fails it prints the commands from CONTRIBUTING.md, and `--postgres` installs the server only. `vibey doctor` is advisory, because it also checks things only an operator has. `--check` reports state and changes and runs nothing; `--skip-doctor` leaves doctor out. **`vibey-gh check` (without `--ci`) now names a clone whose pre-commit framework hooks are missing or are someone else's**, read from the git common directory so a linked worktree is judged correctly, and only for a repository that declares `.pre-commit-config.yaml`; before, the first signal such a clone got was the Provenance check failing after the push. The `core.hooksPath` message now points at `vibey-gh setup`. CONTRIBUTING.md's first hour and environment setup shrink to the command, and the quality-gates skill (all four agent trees) repeats it. The tenant stays stdlib-only: the engine's own commands are reached by subprocess. `hook_inspector.py` is on the root `.vibey-gh.toml` forbidden list, as the approver can execute it. Part of #1689.
