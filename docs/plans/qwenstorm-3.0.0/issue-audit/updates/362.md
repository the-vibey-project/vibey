## Why
ADR-0044 §6 (`docs/architecture/decisions/0044-job-queue-port-and-loop-services.md`). A parked job holds no delivery. Its answer re-readies it in the same transaction as the answer (today `src/vibey/infrastructure/db/human_gate_repository.py:61-86`; after lane `orm-human-gate`, the same two statements as SQLAlchemy Core in one `self._orm.transaction()`, with `pg_notify`). In the RabbitMQ backend, that same transaction must also start a new dispatch episode and write its outbox row, or the answered job would sit `ready` with no message until the lost-dispatch sweep (#358 child 3) found it.

The PostgreSQL backend's behaviour stays exactly as it is: with no writer, the answer is byte-for-byte `orm-human-gate`'s. `specs/orm-human-gate.md` names this lane as landing after it and building on it. The in-memory `FakeHumanGateRepository` (made PostgreSQL-faithful by `fakes-queue-gates`) learns the same optional redispatch.

Verified at integration `739536ea` (line numbers above are today's; `orm-human-gate` moves them).

## Required behaviour
1. `PostgresHumanGateRepository.__init__(self, orm: PostgresOrmInterface, *, rows: HumanGateRowMapperInterface = GATE_ROWS, dispatch_writer: DispatchOutboxWriterInterface | None = None)`. The default `None` keeps `orm-human-gate`'s behaviour unchanged.
2. With a writer set, `answer`'s re-ready statement becomes, in the same transaction: `update(JOBS).where(JOBS.c["id"] == row["job_id"], JOBS.c["state"] == "awaiting_human").values(state="ready", updated_at=func.now(), dispatch_seq=JOBS.c["dispatch_seq"] + 1, dispatched_at=None).returning(JOBS.c["id"], JOBS.c["project_id"], JOBS.c["dispatch_seq"], JOBS.c["kind"], JOBS.c["run_after"])`. A returned row gets one outbox row through `dispatch_writer.write(conn, JobDispatch(..., not_before=row["run_after"]))` on the same connection. The `pg_notify("vibey_job_ready", …)` stays.
3. Answering a gate whose job is no longer `awaiting_human` writes no outbox row (today's guard: the update returns no row).
4. Build the statement from the `JOBS` table constant `orm-human-gate` already uses; typed literals only (no `text()`, no `literal_column`).
5. **The fake.** `FakeHumanGateRepository` (`tests/fakes/queue.py`) accepts a keyword `dispatch_writer: FakeDispatchOutboxWriter | None = None` and a keyword `dispatch_records: FakeDispatchingJobRecords | None = None` (whose `dispatch_seq` map it bumps). With both set, an answer that re-readies an `AWAITING_HUMAN` job bumps its sequence and writes one dispatch at the job's `run_after`; an answer to a job that moved on writes none. Without them its behaviour is unchanged.
