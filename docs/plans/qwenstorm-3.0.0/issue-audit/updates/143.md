# Human user interfaces: web, mobile and desktop clients over one conductor API, all working on the fully sovereign install

## Summary

Today a human can drive vibey only from the command line and a one-screen terminal
dashboard. The ask is every human surface that can be built, **Windows-specific work
excepted**:

- an Android app
- an iOS app
- a macOS desktop app
- a Linux desktop app
- a Next.js web app

Every one must work against the **completely sovereign** install, with paid models
addable afterwards. All of them need the same thing first: an HTTP API (plus a live event
stream) for the conductor, which does not exist. Runbooks 08 (clients), 12 (integration
surfaces) and 07 (store submissions) already design this. The canon since ratified narrows
the targets: Arch Linux and macOS are the default operating systems (8.h), and every
supporting service (push, stores) takes its sovereign option first (8.a/8.b).

## Why

- **The operator's ask** (2026-09-15): "right now this is only really human usable from a
  TUI or CLI, that's a problem!" "all UI platforms need to work on the completely sovereign
  version."
- **8.h** (`src/vibey_tools/gh/docs/doctrines.md:326-333`): Arch Linux is the default
  sovereign OS and macOS the default paid OS. A change that works on one but not the other
  is not done. This matches "ignore anything windows specific".
- **8.a / 8.b** (`:99-194`): every surface defaults to the freest self-hosted option. For
  clients that means push notifications through a self-hosted relay rather than only
  Apple/Google push, and FOSS distribution (F-Droid, AUR) beside the vendor stores.
- **2.b** (`:30`): installable wherever users already are, published by automation.
- **Doctrine 3** (`:32-35`): every API surface has a working example. **7 / Bill of Rights
  I**: no reader is lost. **12.c** (`:455`): the API contract is declared (OpenAPI,
  committed, drift-tested).
- **Bill of Rights IV**: full capability free. No client needs an account on a hosted
  platform.

## Scope / Required behaviour

1. **`vibey server`**: an HTTP API over the application layer. It covers:
   - projects, jobs, gates (read and answer), engines and health, budget, and the ledger
     (cursor-paged)
   - a live event stream (SSE) with the depth parameter from runbook 08
     (`phase | job | ledger | engine | raw`)
   - token auth, loopback-bound by default
   The OpenAPI schema is committed and drift-tested.
2. **A typed client** generated from the schema, shared by every client.
3. **Web (Next.js):**
   - the projects list and phase pipeline
   - the queue with lease ages
   - gate answering, including the `--raw` JSON grammar
   - engines and rotation, budget, and log drill-down
4. **Mobile (one React Native/Expo codebase for iOS and Android):** gate answering, budget
   approvals and the log viewer. Push through a **self-hosted** relay by default, with
   Apple/Google push declared.
5. **Desktop (macOS + Linux):** a shell around the web UI with a tray showing the live
   phase. Packages: macOS dmg, Arch (AUR/PKGBUILD) first per 8.h, then AppImage/deb/rpm.
6. **TUI** completed to the same screen set.
7. Every surface works with **no paid engine declared**. Paid engines appear only when
   declared.

## Proposed child issues

The API comes first. Children 1–4 unblock everything else.

1. **feat(api): `vibey server` with read-only projects and jobs.** A FastAPI app in
   `src/vibey/infrastructure/api/` behind an application port. `GET /projects`,
   `GET /projects/{id}` and `GET /projects/{id}/jobs` are built from the same application
   queries `vibey status --json` uses. Token auth, bound to 127.0.0.1. Tests with the
   in-memory fakes. (Sized for one lane.)
2. **feat(api): gate listing and answering.** `GET /gates` and
   `POST /gates/{id}/answer` (defaults, choice, raw JSON), mapping to the same handler
   `vibey answer` uses. Tests.
3. **feat(api): the ledger event stream (SSE) with a depth parameter and cursor
   backfill.** Tests.
4. **build(api): commit the OpenAPI schema and a drift test.**
5. **Design needed first — clients toolchain and CI lanes** (Node for web and mobile, Rust
   for Tauri), and where clients live. Record the decision (ADR).
6. **feat(web): the projects and pipeline view (Next.js)**, after 1 and 5.
7. **feat(web): gate answering**, after 2.
8. **Design needed first — self-hosted push** (for example a UnifiedPush-compatible
   distributor run in the cluster, with Apple/Google push declared).
9. **feat(mobile): gate answering (React Native)**, after 2 and 8.
10. **feat(desktop): Tauri shell + tray, macOS and Arch packages first.**
11. **feat(tui): the remaining screens** (gates, logs by depth).
