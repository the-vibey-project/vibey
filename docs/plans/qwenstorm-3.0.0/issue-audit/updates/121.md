# The loops as services in one cluster: two loops, one instance per model, on the bus, installed by one Helm chart and proven on minikube

## Summary

The original ask had two halves:

1. Merge the separate `*loop` repositories into one. **Done differently:** they were
   absorbed into this repository with history (ADR-0021) and ship as one distribution
   (ADR-0037). No `vibey-loops` repository is needed.
2. Run the loops as microservices in a Kubernetes cluster (Helm; kustomize was also named),
   spun up or down elastically as the work demands. **Not done yet, and reshaped by
   ratified canon.** Sub-doctrine 8.c (2026-09-22) says the family runs **exactly two
   loops**: `sovereignloop` (what qwenloop becomes) and `paidloop` (with claudeloop,
   codexloop, cursorloop and agyloop as adapters). Each runs as **a single instance per
   model**, fed by **a queue on the RabbitMQ bus**. "Throughput is raised by giving the one
   instance more capacity, never by starting another." So "elastic" means a loop service
   can go from 0 to 1 instance and back, and its capacity (prefetch) can be tuned. It never
   means N copies of the same model.

The cluster half is being built: ADR-0044 (proposed) and QwenStorm #348–#381 (open). This
issue becomes the operator's tracker. It closes when both loop services run on minikube
from the chart and a run goes through each. The operator asked: "once confirm it's fully
done and working, tell me and we can decide what to do from there".

## Why

- **8.c** (`src/vibey_tools/gh/docs/doctrines.md:196-234`): two loops, one instance per
  model, work taken from a queue on the bus, two rotation layers with dead-letter queues
  and idempotency. "Nothing starts a second instance of a loop to go faster, and nothing
  spawns a loop directly." It is backed by the 2026-09-22 measurement: three qwenloop
  sessions on one model server all timed out, and one at a time they run.
- **8.b** (`:128-135`, `:163-166`): engines default to `sovereignloop`, and `paidloop` is
  declared-only. The bus defaults to RabbitMQ in the operator's own cluster. OpenCode is
  repealed in favour of VS Code.
- **8.g** (`:316-324`): every loop records latency, throughput, queue depth and waiting
  time. Capacity is chosen from that evidence.
- **12.c** (`:455`): the cluster is declared in the chart and reconciled, never clicked.
- ADR-0021 (one tree), ADR-0025 (Kubernetes operator/CRD/KEDA), ADR-0026 (tini as PID 1),
  ADR-0037 (one distribution), ADR-0044 (proposed: the job queue is a port, RabbitMQ
  dispatches, every loop engine runs as a long-lived service).

## What is stale in the original text

- "`vibey-loops` repo … merged into a single monolithic … repo": superseded by ADR-0021 and
  ADR-0037. The runners live at `src/vibey_runners/{claude,codex,cursor,agy,opencode,qwen}`
  and the whole tree ships as `vibey`.
- "individual loops able to be spun up or down elastically": elastic replica scaling of a
  loop contradicts 8.c. Spin-up and spin-down (0↔1) and capacity tuning remain compatible.
- **ADR-0044 is itself behind the canon.** It was written against 8.c as ratified by #325
  (per-engine services: "one Deployment per loop service", "qwenloop and opencode are
  enabled by default", ADR-0044 §13 and §15). The #392 amendment (2026-09-22) changed that
  to **two loops** with inner adapter rotation, and **repealed OpenCode**.
- The amendment is already drafted: **draft ADR-0046 "Two loops"** (QwenStorm spec
  `specs/ADR-two-loops.md`, proposed, not yet in the tree). It amends ADR-0044's §2 run
  topology, §13 one-service-per-engine and §15 loop-service chart. It keys run routing,
  control, probes and dead letters by **loop**, with a per-model seat host. The per-engine
  loop-service lanes #366–#375, #377 and #379 are therefore partly superseded by its
  design, and #378's dependency list points at those lanes. Each needs re-cutting
  before it merges.

## Scope / Required behaviour

1. `sovereignloop` and `paidloop` each run as a long-lived service, **one instance per
   model**, consuming its own queue on RabbitMQ with dead-letter queues and idempotency
   (8.c). `paidloop`'s adapters (claudeloop, codexloop, cursorloop, agyloop, and VS Code on
   a paid provider) rotate inside it. `sovereignloop` holds the local models and VS Code on
   a local provider.
2. The Helm chart installs both loop services. `sovereignloop` is on by default.
   `paidloop` is declared-only (8.b), off unless a human declares it in values.
3. A loop service can be scaled 0↔1 (KEDA on its queue) and its capacity (prefetch) tuned
   from measurements (8.g). Replicas above 1 per model are refused, with a loud message.
4. Every caller (worker, `vibey work`, storms, CLI) submits to the loop's queue. Nothing
   spawns a runner directly when `[engines] invocation = "service"`.
5. On minikube: `helm install` brings up the broker, both loop services and the worker. A
   scripted run is served by each loop, and an instance killed mid-run returns its work to
   the queue (restart, never a second copy).
