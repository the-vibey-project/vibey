## Summary

This is the substrate the commercial features (#86, #88) and the marketplace (#90) stand

history, **config boards** for managing a fleet's configuration, reporting dashboards, and
one correlation ID tracing a delivery end to end. The doctrine boundary in the original

grows a sign-in requirement. Three ratified rules now reshape parts of it:

- **10.b** (2026-08-29): payment methods and history are **cryptocurrency** only.
- **12.c** (declared state): a "config board" may edit configuration only by writing it to
  the repository through a reviewed change (a pull request), and never by clicking live

## Scope / Required behaviour

In the original's order.

1. **Roles** (operator / engineer / client / bot), least privilege by default, enforced at
   the application layer behind an interface. Bots carry machine identities labelled as
   such (Constitution III.4).
2. **The audit trail:** every privileged action records actor, authority (role + grant),
   time and object, append-only and hash-chained (reusing `ChainedAuditRecord`), and is
   mirrored to the security-events surface (Wazuh by default).
3. **SSO and accounts** (hosted platform only): OIDC/SAML against a **self-hosted identity
   provider by default** (8.b spirit), with hosted IdPs declared-only.
4. **Payment methods and history:** crypto wallets and settlement records only (10.b),
   wired to #88's milestones and #148's rail.
5. **Config boards:** a UI that reads the fleet's declared configuration and proposes
   changes **as pull requests** to each repository (12.c). It never writes live state.
6. **Dashboards:** throughput, phase timings, estimate versus actual (#88/#134), spend and
   margin trend, all from ledger data.
7. **Tracing:** one correlation ID on every ledger event *and* log line across the six
   phases and every repository touched.
8. **The free-path guard:** a conformance test proves the FOSS toolchain runs with no
   sign-in, and an import-linter contract proves no free-path module imports the hosted
   layer.

## Doctrine boundary

Accounts are for the **hosted, commercial platform**. The FOSS toolchain never grows an
account requirement: every repo in the family keeps working standalone, offline from this
platform, with no sign-in — full capability, forever. If a feature only works with an
account, it belongs to the hosted layer and must have no hook inside the free tools.

## Sequencing

Roles + audit trail first (they gate everything else being trustworthy), then SSO/accounts,
then payments, then boards/dashboards on top of data that by then exists.
