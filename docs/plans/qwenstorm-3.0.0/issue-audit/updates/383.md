Part of the **QwenStorm for 3.0.0**. A local sovereign lane (qwenloop until ADR-0046's rename lands) implements this issue; the result is reviewed and verified before it becomes a pull request.

This issue is child lane 1 of the model-catalogue work. The other children are listed at the end.

## Why
Sub-doctrine 8.d (`src/vibey_tools/gh/docs/doctrines.md:236-269`) says vibey supports every
gold-standard free model that runs on a Linux or macOS laptop. For each supported model:
- its weights are pinned in the model catalogue (source, revision and digest);
- it runs on both local backends, Ollama and llama.cpp;
- the catalogue records the evidence for each choice and the date it was made (10.f).

Where two models are otherwise comparable, the one under the freer licence wins: an OSI-approved
licence beats a custom one. The designated default for this era is **GPT-OSS 20B on Ollama**
(`gpt-oss:20b`). #387 made it the default of vibey and qwenloop (integrated at `ddf2bf05`).

Today there is no catalogue. There is one pinned llama.cpp profile, Qwen2.5-Coder-14B-Instruct
Q5_K_M, plus a vLLM profile
(`src/vibey_runners/qwen/src/qwenloop/infrastructure/profiles.py:9-31`, `PROFILES` at `:33`), in the
shape `ModelProfile` (`src/vibey_runners/qwen/src/qwenloop/domain/model.py:34-44`). Nothing records
an Ollama tag, a licence, a RAM floor, or why a model was chosen.

The operator measured on 2026-09-22 (#383 comment, M5 24 GB, llama-server build 10566) that
Ollama's GPT-OSS 20B file does not load in llama.cpp: `unknown model architecture: 'gptoss'`. So
the llama.cpp side must pin its own GGUF and never share blobs with Ollama.

This lane adds the catalogue as data (12.c) with its first two entries. It changes no default and
no selection.

## Required behaviour
1. `src/vibey_runners/qwen/src/qwenloop/domain/catalogue.py` (pure, stdlib only) declares:
   - `@dataclass(frozen=True, slots=True) class OllamaArtifact`: `tag: str`.
   - `@dataclass(frozen=True, slots=True) class ModelEntry` with these fields:
     - `name: str`: a slug such as `"gpt-oss-20b"`;
     - `family: str`;
     - `total_params_b: float` and `active_params_b: float`;
     - `license_spdx: str`, for example `"Apache-2.0"`;
     - `license_osi: bool`;
     - `min_ram_gib: int` and `context_window: int`;
     - `ollama: OllamaArtifact | None`;
     - `gguf: ModelProfile | None`: the llama.cpp pin, reusing `ModelProfile` with
       `backend=Backend.LLAMA_CPP`;
     - `evidence: str` and `recorded: str`: an ISO date, `YYYY-MM-DD`;
     - `unverified: tuple[str, ...] = ()`: the backends named here were never test-loaded (10.f).
   - `class ModelCatalogue(entries: tuple[ModelEntry, ...] = CATALOGUE)`:
     - `__init__` raises `ValueError` on a duplicate `name`, a duplicate Ollama tag, or an entry
       with neither artifact;
     - methods `entries()`, `get(name) -> ModelEntry` (raises `KeyError` naming the known names) and
       `by_ollama_tag(tag) -> ModelEntry | None`.
2. `CATALOGUE` holds exactly two entries:
   - **qwen2.5-coder-14b**:
     - family `"qwen2.5-coder"`, 14.7 B total and 14.7 B active, `"Apache-2.0"`, OSI True;
     - `min_ram_gib=16`, `context_window=32_768`;
     - Ollama tag `qwen2.5-coder:14b`;
     - `gguf=PORTABLE`, the existing profile unchanged;
     - evidence: "previous default; 215 s for a ten-turn session at 32,768 tokens on an M5 24 GB
       (llama.cpp)", recorded `"2026-09-22"`.
   - **gpt-oss-20b**:
     - family `"gpt-oss"`, 20.9 B total and 3.6 B active, `"Apache-2.0"`, OSI True;
     - `min_ram_gib=16`, `context_window=131_072`;
     - Ollama tag `gpt-oss:20b`;
     - evidence: the 8.d paragraph's measurement (86 s for ten turns, 131,072 tokens, 13.1 GB
       resident, M5 24 GB, Ollama), recorded `"2026-09-22"`;
     - its `gguf` is pinned from `ggml-org/gpt-oss-20b-GGUF` **only with values read from the
       source**:
       - `curl -s https://huggingface.co/api/models/ggml-org/gpt-oss-20b-GGUF` gives the revision
         (`sha`);
       - `curl -s https://huggingface.co/api/models/ggml-org/gpt-oss-20b-GGUF/tree/<sha>` gives, for
         the single-file GGUF, its `path`, `size` and `lfs.oid` (the sha256);
       - quantization is `"MXFP4"` if that is what the file name says.
       - If the lane host cannot reach huggingface.co, set `gguf=None` and
         `unverified=("llama.cpp",)`, and name it as a follow-up in the commit body. Never type a
         digest from memory.
   - Every entry that was not test-loaded in a backend lists that backend in `unverified`. This lane
     loads nothing.
3. `profiles.py` keeps `PORTABLE`, `NVIDIA_BF16` and `PROFILES` exactly as today, so every existing
   caller works unchanged. It adds `CATALOGUE_PROFILES`, a dict from each GGUF-pinned entry's
   `gguf.name` to its profile. The llama.cpp portable profile can now be chosen by name from the
   catalogue.
4. `src/vibey_runners/qwen/src/qwenloop/domain/interfaces/catalogue_interface.py` declares a
   `@runtime_checkable` Protocol `ModelCatalogueInterface` with the three methods. Import the domain
   types under `TYPE_CHECKING`, copying the style of the domain `interfaces/` package in that
   directory.
5. A test asserts that `ModelCatalogue().get("gpt-oss-20b").ollama.tag == DEFAULT_ENDPOINT_MODEL`
   (`domain/config.py:15`). The default and the catalogue can then never drift.

## Proposed child lanes

### 1. feat(qwenloop): a model catalogue as data — each entry pins its GGUF, its Ollama tag, its licence and the evidence for choosing it (this issue)
The catalogue's schema and its first two entries: Qwen2.5-Coder-14B (existing) and GPT-OSS 20B. The
default is tied to the catalogue by a test. No selection changes. Specified above.

### 2. feat(qwenloop): catalogue Qwen3.6-27B, Qwen3.6-35B-A3B and Qwen3.8-27B on both backends
The lane adds one entry per model:
- the Ollama tag, read from ollama.com/library;
- the llama.cpp GGUF, pinned from `unsloth/<model>-GGUF` with its revision, sha256 and size taken
  from the Hugging Face API exactly as in lane 1;
- the licence (SPDX) and the RAM floor.

Each artifact is test-loaded in its own backend on a machine with the RAM. The GGUF must not come
from Ollama's blob store. The load evidence is recorded in the entry: machine, date, and a one-line
result such as `llama-server` loading and answering one prompt. A backend that could not be loaded
is listed in `unverified` and is never claimed. A model that cannot be pinned is left out and named
in the commit body as a follow-up. This lane is data plus tests. The downloads are operator
evidence, not CI.

Depends on lane 1.

### 3. feat(runners-common): one memory probe for the family
The lane moves vibey-gh's physical-memory reading (`src/vibey_tools/gh/vibey_gh/fit.py:273`,
`sysctl -n hw.memsize` on macOS) into the dependency-free family package
`src/vibey_runners/common`. It becomes a class `MemoryProbe`, with its interface, a `/proc/meminfo`
reading for Arch Linux (8.h), and an injected command runner and file reader as its seams.

vibey-gh's `fit` then uses it, so there is no second copy (10.e). qwenloop adds
`vibey-runners-common` to its dependencies, which is dependency-free and on the same Python floor.

Tests fake the command runner and the file. None patches `subprocess` or `platform`. Depends on
nothing.

### 4. feat(qwenloop): with no model configured, the sovereign loop picks the 8.d default wherever it fits, and a RAM-tier default only where it does not
The selector is pure and injected with the memory probe from lane 3:
- An explicit model (config, `QWENLOOP_MODEL`, flag) always wins.
- Otherwise it picks `gpt-oss:20b` whenever the machine's RAM is at least that entry's
  `min_ram_gib`. This is 8.d as ratified: "on a machine it does not fit, the catalogue's default for
  that machine's tier applies".
- Only below that floor does it take the smaller tier's default from a tier table held as catalogue
  data, with evidence and date.
- Between comparable models, an OSI licence wins (8.d).
- The chosen model and its reason are logged and written to the run's recorded settings (#382's
  telemetry, 8.g).

**Operator decision owed.** The operator's tier table names Qwen3.6-35B-A3B for 48–64 GB and DeepSeek
V4 Flash for 128 GB as *defaults*. That contradicts ratified 8.d, which keeps GPT-OSS 20B wherever
it fits. Either 8.d is amended (Article IV.2) or those rows become opt-in alternatives. The 8 GB
row's Gemma 4 E2B (a custom licence) over Qwen 3.5 4B (Apache-2.0) and the 16 GB row's Llama 3.1 8B
need the same licence check.

Selection also feeds ADR-0046 §4's residency policy: one resident model per machine.

Depends on lanes 1 and 3.

### 5. feat(qwenloop): reasoning channels never reach tool-call or answer parsing
The lane parses llama.cpp's `reasoning_content`, Ollama's OpenAI-compatible `reasoning` / native
`thinking`, and Qwen3's `<think>…</think>` out of the stream qwenloop's agent loop reads. Reasoning
text is kept for the run log (7.c), but it is never parsed as a tool call, as JSON, or as the done
marker.

The tests use recorded real responses from `gpt-oss:20b` on Ollama and on llama-server. vibey's own
DESIGN/DECOMPOSE parsing already reads only `message.content`, via #387's fixture in
`tests/infrastructure/engines/test_ollama_chat.py`.

Depends on lane 1.

### 6. feat(qwenloop): `qwenloop model verify <entry>` and `qwenloop doctor` report the selected model, its backend and its state
- `verify` re-hashes a cached GGUF against the catalogue pin, using `ModelCache` and its injected
  `opener`, or asks the attached Ollama's `/api/tags` for the tag.
- `doctor` prints the selected model, why it was chosen, the backend, and whether the model is
  installed or served, with the fix command.

vibey's own doctor line for the model belongs to the installer wave's `installer-doctor` lane, not
here.

Depends on lanes 1 and 4.
