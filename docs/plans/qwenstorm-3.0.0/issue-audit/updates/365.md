Part of the **QwenStorm for 3.0.0**. A local sovereign lane (qwenloop until ADR-0046's rename lands) implements this issue; the result is reviewed and verified before it becomes a pull request.

## Why
ADR-0044 §16 (`docs/architecture/decisions/0044-job-queue-port-and-loop-services.md`). A port with two implementations is only a port if one suite binds both. `tests/contracts/` already runs a contract against a fake and PostgreSQL (`tests/contracts/test_rotation_cursor_contract.py`, parametrized `["fake", "postgres"]`). The operator's standard adds a third obligation: the in-memory fakes the default run relies on (`FakeJobRepository`, made PostgreSQL-faithful by `fakes-queue-gates`, and the RabbitMQ fakes of #357–#363) must behave like the real backends, and the same suite is what proves it.

The protected chaos test (`tests/infrastructure/db/test_chaos.py:50-170`) pins the PostgreSQL backend's tally: zero double commits, zero lost jobs, every job terminal. The RabbitMQ backend needs the same tally with **consumers killed**, not tasks abandoned. It goes in a new file, because the protected one is never edited.

Every item in `tests/contracts/` is marked `integration` by its conftest (`tests/contracts/conftest.py:19-21`), so the default run would never reach the no-service backends. This lane narrows that hook for its own `queue` parameter only.

Verified at integration `739536ea`.

## Required behaviour
1. `tests/contracts/test_job_queue_contract.py` defines a fixture `queue` parametrized over five backends. Each yields a `QueueHarness` (a small class in the module) with `repo`, `gates`, a `clock` it can advance where the backend allows, and `async def settle()`:
   - `"fake"`: `FakeJobRepository` and `FakeHumanGateRepository` over one `InMemoryQueueStore`; `settle()` does nothing. No service.
   - `"rabbitmq-fake"`: `RabbitMqJobRepository` (#363) over `FakeDispatchingJobRecords` + `FakeDispatchOutboxWriter` (#357, #358), `FakeDispatchRelay` over the real `DispatchPublisher` (#360), the real `ProjectDeliveries` (#361) and `InMemoryAmqpClient` (#351), with `FakeHumanGateRepository` carrying the fake redispatch (#362); `settle()` drains the fake relay and calls `expire()` on every wait tier. No service.
   - `"postgres"`: `PostgresJobRepository` and `PostgresHumanGateRepository` over the migrated database; `settle()` does nothing.
   - `"rabbitmq-memory"`: `RabbitMqJobRepository` over `DispatchingJobRecords`, `DispatchRelay` and `InMemoryAmqpClient`, with `PostgresHumanGateRepository(orm, dispatch_writer=...)`; `settle()` drains the relay and expires every tier.
   - `"rabbitmq"`: the same over a real broker, skipped unless `VIBEY_TEST_AMQP_URL` is set; `settle()` drains the relay and waits for the shortest tier.

   The PostgreSQL fixtures are requested lazily (`request.getfixturevalue`) only for the three service-backed parameters, so the two no-service parameters never touch a database.
2. `tests/contracts/conftest.py`'s `pytest_collection_modifyitems` keeps marking every item `integration`, **except** an item whose `callspec.params.get("queue")` is `"fake"` or `"rabbitmq-fake"`. No other test in the directory is affected (the rotation contract's parameter is `repo`).
3. The contract tests assert identical observable behaviour across every backend:
   - enqueue is idempotent;
   - an empty queue claims `None`;
   - a dependency blocks the claim until it succeeds;
   - a future `run_after` blocks the claim;
   - `ack` is fenced (a second owner is refused);
   - `defer(retry_at=now)` makes the job claimable again after `settle()`;
   - `park` holds the job, and `answer` makes it claimable again (after `reap()` and `settle()` on RabbitMQ);
   - an expired lease is claimable again after `reap()` (and `settle()` on RabbitMQ);
   - a job whose every delivery was abandoned parks as `delivery_exhausted` (#356 on PostgreSQL and the fake; the delivery limit on RabbitMQ);
   - `grant_attempts` widens and never narrows;
   - `count_unsettled` and `queue_depth` agree across backends for the same script.
4. `tests/infrastructure/queue/test_rabbitmq_chaos.py` (`@pytest.mark.slow`, `@pytest.mark.integration`, real broker and PostgreSQL only):
   - 8 workers, each with its **own** `AmqpClient` (its own connection), `ProjectDeliveries` and `RabbitMqJobRepository`;
   - 300 jobs with `max_attempts=1000`;
   - with probability 0.2 a worker "crashes": it calls `await client.close()` without settling, which makes the broker return its unacknowledged deliveries, and a fresh worker replaces it;
   - a concurrent `reap()` loop runs every 50 ms with `reconcile_interval_seconds=0` (#348 allows 0).

   The asserted tally has the same shape as `test_chaos.py:136-150`: executions equal commits plus refused, no double commit, no lost job, every job `succeeded`. It prints the tally.
