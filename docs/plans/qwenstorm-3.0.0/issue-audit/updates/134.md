# The feasibility and cost engine: every coordinate measured, cost in both lanes, the repair gradient, proven against real runs

## Summary

Before any run, vibey should say in plain numbers:

- whether the job can finish through the whole pipeline
- how long it will take
- what it will cost, in both the paid and local lanes
- how far each of the eighteen coordinates (six materials × availability, stability,
  reliability) is from peak
- what to repair first

The calculus exists as code. The eighteen-coordinate evaluator, the nine-stage path and
agency-first reporting all ship as `vibey-gh estimate`, and the conductor's preflight
consults it. But only **2 of 18 coordinates are measured**. Cost is `unknown`. The duration
dilation φ is unspecified, so there is no gradient, and the published forecast reports
"materials measured: 0/18". This epic finishes it: one probe per material, a cost integral,
a measured φ, the gradient, and a validation harness that grades predictions against real
runs.

## Why

- **8.g always measured** (`src/vibey_tools/gh/docs/doctrines.md:316-324`): "Nothing runs
  unmeasured; a component that cannot report its measurements is incomplete."
  Measurements join the ledger and drive rotation weights, lane capacity and defaults.
- **10.d cloud-grade clearance** (`:395-410`): clearance is re-verified at every transition
  "along the pipeline from install through main validation". That is exactly #134's stage
  list. A lapsed criterion is overridden loudly, naming its threshold, current measurement
  and the bill to restore it. This is the report #134 asks for.
- **10 decomposition clarification** (`:371-383`): read both sides of the fit (hardware
  and model), decompose until it fits, and fail loudly at the floor.
- **10.f** (`:419`): unmeasured stays `unknown` and lowers confidence, never defaults.
- **8.a** (`:99-118`): the local lane's cost is real (generation-seconds). Paid credit is
  agency.
- **7.c** (`:82-91`): every measurement is written to the ledger as it happens.

## Scope / Required behaviour

1. **One measured probe per material**, each writing its reading to the ledger (7.c) and
   returning `unknown` with a reason when it cannot look:
   - *network*: reachability, latency and loss to each required endpoint (declared per
     stage in `[estimate]`)
   - *hardware*: stability (paging pressure and free-page series), reliability (thermal /
     CPU headroom, macOS and Arch Linux per 8.h)
   - *software*: pins against installed versions, runner health, config drift against
     `vibey-gh check`
   - *agent*: availability, load and historical success rate from engine health and ledger
     outcomes
   - *information*: required inputs present and fresh (spec, docs, credential validity
     through the secrets surface)
   - *agency*: merge rights and token scopes through the forge adapter (#138), ruleset
     bypass, and paid credit balance
2. **Stability and reliability** are computed from series (variance, success rate), not
   from single readings.
3. **Cost** `C(o)`: the paid lane in dollars (ledger `cost_usd`), and the local lane in
   generation-seconds (qwenloop timing), shown separately and together.
4. **φ measured**: the dilation each shortfall imposes on duration is fitted from
   predicted-versus-actual records. Only then is `T(o)` computed and the repair ranking
   emitted as the gradient `−∇_d T`.
5. **The report** matches the issue's layout. Agency shortfalls come first, and an
   impossible job names its coordinate immediately (10, 10.d).
6. **The validation harness** records each prediction beside the actual outcome (the
   stage reached, duration, cost) and grades it through `GradedEstimator`.

~~~~markdown
## Ask

Bake a **fully autonomous billing and feasibility engine** into the project, derived from the six-materials calculus (paper: *The mechanics of the governance dilemma*). Before any run, the agent is told — plainly, in numbers:

1. **What this run will cost.**
2. **How long it will take.**
3. **How close the system is to long-term stable peak performance**, per coordinate.
4. **Exactly what to adjust**, at this moment, to converge back toward peak.
5. **Whether the job can complete at all** — through the entire pipeline, not just the next step.

## The state vector

Eighteen coordinates: six raw materials x three properties.

| Material | measured from |
|---|---|
| Network | reachability probes, latency and loss to each required endpoint |
| Hardware | memory, free pages, paging pressure, thermal and CPU headroom |
| Software | tool versions against pins, runner health, config drift |
| Agent | model/human presence, load, historical success rate |
| Information | required inputs present and fresh (specs, docs, credential validity) |
| Agency | permissions actually held: merge rights, token scopes, ruleset bypass, credit balance |

Each carries **availability** (present now), **stability** (variance over time), and **reliability** (correct when used). `vibey-gh fit` already measures the hardware-availability and software-availability coordinates; this generalises it to all eighteen.

## Feasibility across the whole pipeline

The verdict must cover every stage, because a run that dies at stage seven wasted stages one through six:

install -> interview -> feature branch -> develop -> develop deployment -> develop validation -> main -> main deployment -> main validation

Each stage declares its requirement vector; the run is feasible only if the state dominates that requirement at every stage it must pass. **Agency shortfalls are the common killer and must be reported first** — a run that cannot merge is infeasible however healthy the hardware, which this project demonstrated repeatedly tonight.

## The report

    vibey-gh estimate --operation "promote 1.65.0"

      feasible: NO - blocked at stage 'main' (agency: merge rights absent)
      cost:     $0.00 local lane (paid lane at zero credit - agency shortfall)
      duration: 14m 20s projected for stages install..develop-validation
      distance from peak:
        network      0.81  stable
        hardware     0.62  free memory 8.8%, below the 20% setpoint
        software     1.00  pins current
        agent        0.94  local reviewer available, reliability 0.31 on nuanced calls
        information  1.00
        agency       0.20  no merge permission; paid credit exhausted
      first repair (steepest descent): restore agency - grant merge rights or fund the paid lane
      second:                          hardware - free 3 GB or reduce concurrency to 8

## Acceptance

- Every number traceable to a measurement, never a default; unmeasurable coordinates report *unknown* and lower the confidence rather than being invented (doctrine 10).
- Feasibility verdicts proven against real runs: a job called infeasible must actually fail at the named stage, and one called feasible must complete.
- Cost accounting covers both lanes — paid API spend and local generation-seconds — because sovereignty means the local lane's cost is also real.
- The repair ranking is the gradient, not a heuristic list, and is shown to reduce time-to-peak on a real recovery.
- Fails loudly at the floor per doctrine 10: an impossible job says so immediately, naming the coordinate that makes it impossible.
- Zero new runtime dependencies.
~~~~
