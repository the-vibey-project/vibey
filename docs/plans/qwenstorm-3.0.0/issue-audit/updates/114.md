# Ledger storage tiers: partitioned PostgreSQL, three lossless retention modes, an opt-in archival node

## Summary

The ledger is append-only and, under sub-doctrine 7.c, must hold ever more of what happened.
It therefore grows without bound. This epic makes growth survivable without choosing
between truth and disk:

- declarative partitioning of `event`
- three configurable, lossless tiers: raw hot window, compressed mid-tier, since-inception
  archive
- automatic ageing through the tiers
- content-addressed chunks with a hash-walk verification
- an opt-in **archival node** role that holds everything
- published benchmarks

Some foundations have landed: a partitioning migration, a `TierConfig` value, a zlib codec,
and a tier manager over an in-memory store. None of it is wired into the running system,
and the rest is unbuilt.

## Why

- **7.c the thorough ledger** (`src/vibey_tools/gh/docs/doctrines.md:82-91`): record
  everything, append-only, "completeness grows by new events". Growth is the design, so
  storage tiers are the price of 7.c.
- **7.a the searchable ledger** (`:72-78`): search must span every tier with one coherent
  answer, for anyone.
- **10 no guarantees** (`:366-383`): storage is never assumed infinite. A machine that
  cannot hold the work fails loudly.
- **10.a censorship resistance** (`:385-388`): archival nodes are how ledgers survive
  erasure.
- **8.b** (`:163-166`): blob storage defaults to self-hosted **Garage** (S3 protocol). The
  archive's segment files have a sovereign default home.
- **8.f** (`:294-314`): blob operations go through the blob surface's single lane on the
  bus.
- **8.g always measured** (`:316-324`): ratio, write amplification and restore latency are
  measured continuously, not once.
- **Non-negotiables** (CLAUDE.md): the ledger is append-only, every job is idempotent under
  replay, and no-loss gate rule R6 depends on the gapless `seq`.

## Scope / Required behaviour

1. **Modes** (config, `[ledger]` table in `vibey.toml`, documented in
   `docs/reference/configuration.md`):
   - *standard*: the latest N records per project raw (N > 0, default set by measurement)
   - *mid-tier*: the latest M records compressed losslessly
   - *archive*: everything since inception as content-addressed, losslessly compressed
     segments
2. **Rotation** runs as a queued job (never a thread waiting on a human). It creates range
   partitions ahead of `seq`, moves records raw → compressed → archive, and verifies each
   copy before removing the source. The job is idempotent under replay.
3. **Chunks** are content-addressed. Identical chunks dedupe, and each chunk's hash chains
   into the ledger's digest story. Archive verification is a hash walk with no
   decompression.
4. **Archive segments** go to the blob surface (Garage by default, 8.b) through its lane
   (8.f).
5. **Reads are tier-aware.** `PostgresLedgerRepository.range()` / `all_for_project()`,
   search, the full-ledger handoff writer and the no-loss gate's R6 digest all return one
   coherent, ordered answer across tiers.
6. **Archival node** (opt-in): holds the complete archive plus hot tiers and serves
   history other nodes compacted away. A non-archival node keeps its windows plus the
   segments it produced.
7. **CLI:** `vibey ledger tiers` (status), `archive`, `restore`, `verify`.
8. **Benchmarks:** ratio, write amplification and restore latency per tier and codec,
   generated by a script from real runs (8.g, 10.f), and published in the docs.

## Acceptance criteria

- [ ] Bit-for-bit reconstruction from mid-tier and archive forms, proven by property tests.
- [ ] A query spanning all three tiers returns the same ordered events as an untiered
      ledger. The no-loss gate's R6 digest over a tiered range equals the untiered digest.
- [ ] Tier transitions under concurrent appends (chaos-style test on real PostgreSQL) lose
      nothing and never break `seq` gaplessness.
- [ ] Archival node behaviour is documented never-lost style: what it stores, serves and
      costs.
- [ ] The benchmark table in the docs is generated from tracked runs.
- [ ] The 100% branch floors hold for domain/application/infrastructure/cli.

~~~~markdown
## Ask

Future-proof the PostgreSQL ledger against storage constraints with **fully aggressive, fully optimized sharding**, and give operators a three-tier retention scheme plus an opt-in archival role — so a ledger that grows forever never forces a choice between truth and disk.

## The three modes (all configurable, all lossless by definition)

1. **Standard mode (the official default)** — the latest **N full, uncompressed ledger records**, N > 0 and operator-configured. Hot reads stay raw: no decompression on the working set, ever.
2. **Mid-tier mode** — the latest **N ledger records under aggressive *and* lossless compression**, N operator-configured. Aggressive and lossless are both load-bearing: maximum ratio, zero information loss, bit-for-bit reconstructible.
3. **Archival mode** — the **full ledger since inception** as one aggressively-and-losslessly compressed dataset. Nothing is ever unrecoverable; the entire history reconstructs bit-for-bit.

Records age through the tiers automatically: raw in standard, compressed at mid-tier, folded into the archive — with the tier boundaries (both Ns) as ordinary config.

## The opt-in archival node

A deployment may opt in to running a **full archival node**: it holds the complete since-inception ledger (mode 3) alongside the hot tiers, serving history that other nodes have compacted away. Opt-in per the no-guarantees family of doctrines — and note the 10.a resonance: full archival nodes are how ledgers survive attempts to erase them. A non-archival node keeps only its configured standard + mid-tier windows plus the archive segments it has produced.

## Sharding requirements

- **Declarative partitioning** on the ledger's natural key (sequence/time), hash- or range-based as benchmarks dictate — chosen for pruning efficiency, not fashion.
- Partition rotation automated (creation, tier transition, archive fold-in) with zero operator ceremony after configuration.
- **Chunking + content-addressed hashing** for the compressed tiers: identical chunks dedupe, every chunk's hash chains into the ledger's own integrity story, and archive verification is a hash walk, not a full decompress.
- Compression candidates to benchmark: zstd (high levels) on columnar-organized segments, PostgreSQL-native options (TOAST tuning, lz4/zstd column compression) for mid-tier, external content-addressed segment files for the archive. Pick by measured ratio × restore-speed, document the numbers.

## Acceptance

- All three modes configurable and covered by tests that prove **bit-for-bit reconstruction** from mid-tier and archival forms.
- Tier transitions exercised under load; a query spanning all three tiers returns one coherent, correct answer.
- Archival-node opt-in documented never-lost style: what it stores, what it serves, what it costs.
- Benchmarks published in the docs: ratio, write amplification, restore latency per tier.

Related doctrine: no-guarantees (storage is never assumed infinite), 10.a (censorship resistance — archival nodes as survival), the living roadmap (this lands on it).
~~~~
