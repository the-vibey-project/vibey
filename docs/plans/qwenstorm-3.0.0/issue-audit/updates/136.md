# The forge-state ledger: every forge artifact captured losslessly, reconstructible at any moment, replayable on any forge

## Summary

A project's code survives any host because git travels. Its issues, change requests,
reviews, releases and checks do not: they live in the forge's database. This epic holds
all of that as a **lossless, content-hashed, forge-neutral record the project owns**. It is
captured incrementally, written into the vibey ledger, reconstructible as of any captured
moment, and **replayable into a clean forge**. The first slice, `vibey-gh forge-snapshot`,
has landed: GitHub only, 9 artifact classes, hash-chained JSONL files, and 33 named
exclusions. What remains is verification, more classes, readers for other forges, the
ledger writer, point-in-time reconstruction, and the GitHub → Forgejo round trip.

Since sub-doctrine 8.b, that round trip is more than a migration tool. A declared paid
forge "relays through the sovereign host rather than replacing it; the sovereign host stays
the source of truth". Capturing GitHub's state and replaying it into the operator's Forgejo
is how that relay holds the whole project, not just its code.

## Why

- **Constitution Article I** (`constitution.md:52-54`) and **Bill of Rights V** (the Right
  to Leave): "the lock-in with no migration path" is the named fear.
- **7.c the thorough ledger** (`src/vibey_tools/gh/docs/doctrines.md:82-91`): the ledger
  holds "as much of what happened as can be recorded … What the ledger does not hold is a
  gap to be closed". Redaction is recorded, never silent.
- **7.a the searchable ledger** (`:72-78`): captured forge state becomes searchable by
  anyone through the explorer that #137 delivered (closed).
- **8.b** (`:138-139`, `:179-186`): Forgejo is the default forge, and a declared GitHub
  relays through it. The sovereign host must be able to hold the relayed state.
- **10.a** (`:385-388`): the forge's state survives the forge.
- **12.a** (`:449-453`): meaning lives in plain structured text. The envelope is neutral.
- **10.f** (`:419`): "could not look" is never written down as "nothing there". The S1
  design already honours this.

## Scope / Required behaviour

1. **S2: verify.** `vibey-gh forge-snapshot --verify DIR` checks every seal, every link and
   every manifest head, and reports the first break per file.
2. **S3: more classes**, each captured or kept as a named exclusion: timelines, commit
   comments, repository metadata, check runs and statuses for change-request heads,
   workflow runs, rulesets and branch protection (permission-gated), and GraphQL-only
   classes after #145's GraphQL design.
3. **Forge-neutral readers:** the snapshot reads through `ForgeAdapterInterface`, so
   Forgejo (the default forge) and GitLab capture with the same envelope. Readers for
   declared forges follow their adapters (#298).
4. **S4: the ledger writer.** vibey-gh stays stdlib-only (`pyproject.toml:30`). It declares
   a `SnapshotStoreInterface` sink. The concrete ledger writer lives in vibey's
   `infrastructure/` and writes sealed records unchanged into a table of their own, tiered
   per #114. Writes are idempotent under replay: the same record digest is written once.
5. **Point-in-time reconstruction:** given the ledger, derive the state of every captured
   artifact as of any captured moment. A query plus a CLI surface.
6. **S5: restore and round trip.** Replay a snapshot into a clean Forgejo, mapping native
   IDs. Capture it again and compare records. IDs are mapped and content must match. Any
   field that cannot round-trip is a documented exclusion.
7. Zero new runtime dependencies in vibey-gh. Every capture runs against a local Forgejo
   with no cloud.

## Acceptance criteria

- [ ] `--verify` detects a removed, reordered or edited line in each class file, with one
      test per failure mode.
- [ ] Every artifact class the Forgejo and GitHub APIs expose is captured or listed in
      `excluded` with a reason. `manifest.json` proves it.
- [ ] A capture from Forgejo and a capture from GitHub produce the same envelope schema.
- [ ] Records reach the vibey ledger through the S4 writer. Re-running a capture writes
      nothing new, as a test proves.
- [ ] A point-in-time query returns an issue's state as of a chosen captured moment.
- [ ] The round trip GitHub → Forgejo on a real repository yields identical records
      (IDs mapped), recorded as evidence (instance, repository, dates, manifest digests).

~~~~markdown
## Ask

Capture **everything a forge actually contains** — issues, issue comments, PR comments, reviews and review threads, timeline events, labels, milestones, releases and asset manifests, check runs and statuses, discussions, rulesets and branch protections, repository metadata, workflow-run records — into a **completely lossless record of the entire system's state at any given moment in time**, stored in **the ledger**, so the whole thing is reconstructible and **completely transferable no matter what software you are running it with**.

This is the antithesis of the Constitution's named fear — *the lock-in with no migration path*. When the forge's entire state lives in the ledger in a forge-neutral schema, the forge becomes a replaceable renderer of state the project owns.

## Shape

- **`vibey-gh forge-snapshot`**: walks the forge API and emits every artifact class as append-only, forge-neutral records — plain structured text (12.a: meaning survives every stack), each record content-hashed, the capture hash-chained (the corpus-index pattern of #259 generalized to live state). Incremental via since-cursors; a full capture and a day's delta use one schema.
- **Forge-neutral nouns**: change-request, not PR; the same abstract vocabulary #243 defines — captured once, replayable anywhere. Snapshot on GitHub, restore on Forgejo: migration becomes `snapshot → replay`, and the fully-local deployment (#243's sovereign rung) inherits its entire history, not just its code.
- **Into the ledger**: records flow to the vibey ledger through an adapter interface, tiered per [vibey#114](https://github.com/adammatthewsteinberger/vibey/issues/114) — the hot window raw, history aggressively-and-losslessly compressed, the archival node holding everything since inception. Governance events (ratifications, supersessions) land immutably, which is the evidentiary substrate Articles IV.5–6 and V.4 assume.
- **Searchable**: once forge state is ledger state, [#247's explorer](https://github.com/adammatthewsteinberger/vibey-gh/issues/247) searches the project's ENTIRE history — every comment, every review, every decision — one search box over law, ledger, and forge alike (7.a: anyone, no matter who; human consumption first).
- **Lossless is testable**: the acceptance proof is bit-for-bit round-tripping — snapshot, restore into a clean forge, snapshot again, identical records (IDs mapped, content identical). Anything the schema cannot round-trip is a named, documented exclusion, never a silent one.

## Acceptance

- Every artifact class a forge exposes via API is captured or named as excluded with a reason — nothing silently dropped.
- Point-in-time reconstruction: given the ledger, the full state of issues/PRs/comments/releases *as of any captured moment* is derivable.
- The round-trip proof above, demonstrated GitHub → Forgejo on a real repository.
- Zero new runtime dependencies; the schema documented never-lost style; snapshot runs offline against a local forge.

Doctrine: 10.a (the forge's state now survives the forge), 12.a (translatability — the schema is plain structured text), 7.a (searchable by anyone), Article I (the lock-in fear answered), vibey#114 + #243 + #247 (this unifies all three epics into one migration-proof whole).
~~~~
