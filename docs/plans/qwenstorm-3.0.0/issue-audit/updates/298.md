# Bitbucket: a declared-only forge adapter on the vibey-gh forge standard

## Summary

Add Bitbucket as a forge that vibey-gh can drive through the forge-neutral standard
(`ForgeAdapterInterface`), the same way the GitHub, GitLab and Forgejo adapters already do.
The standard already names Bitbucket (`ForgeKind.BITBUCKET`) and deliberately refuses it at
config load "until its adapter exists". This issue is that adapter: a transport, an adapter,
selector and config wiring, fixture-level contract tests, and an opt-in live test. Under
sub-doctrine 8.b, Bitbucket is a hosted platform, so it is **declared-only**: it is used only
when a human writes `kind = "bitbucket"` into `.vibey-gh.toml`, and it never becomes a default.

## Why

- **The operator asked for it** ("add support for bitbucket", 2026-09-19). The one-line seed
  is read here as "Bitbucket as a forge vibey-gh can run on". That reading comes from the
  repository: `ForgeKind` lists `bitbucket` next to github, gitlab and forgejo, and
  AGENTS.md:99 lists `github/gitlab/bitbucket` together as forges.
- **8.b (one protocol, adapters per platform, paid declared-only)**:
  `src/vibey_tools/gh/docs/doctrines.md:138-139` makes self-hosted Forgejo the default forge.
  Hosted forges are declared-only. `:168-177` requires that every surface speak one
  vibey-owned protocol realised by one adapter per platform. For forges that protocol is
  `ForgeAdapterInterface`. `:179-186` says a declared paid platform **relays through the
  sovereign host rather than replacing it**.
- **12.c (declared state, configurable)** `doctrines.md:455`: the platform is chosen by
  configuration, and the adapter never hard-codes it.
- **9.b (declared seam)** `doctrines.md:349`: every new class gets an interface beside it,
  and a test double exists from the first day.
- **10.e (family first)** `doctrines.md:417`: the adapter reuses the family's transport
  pattern (`gh_transport.py`, `gitlab_transport.py`, `forgejo_transport.py`) rather than
  pulling in a third-party Bitbucket SDK. vibey-gh declares `dependencies = []`
  (`src/vibey_tools/gh/pyproject.toml:30`).

## Scope / Required behaviour

1. `[platform] kind = "bitbucket"` loads, with `host` (Bitbucket Cloud's API host by default,
   or a self-managed host), `repository` (`workspace/repo-slug`) and `token_env`.
2. `BitbucketTransport` (stdlib `urllib` only, like `forgejo_transport.py`) handles
   authentication from the named environment variable, pagination, and error mapping. Its
   interface sits beside it in `interfaces/`.
3. `BitbucketForge` implements every verb of `ForgeAdapterInterface`. The noun mapping below
   must be checked against the official Bitbucket REST API documentation when the adapter is
   built, not assumed:
   - pull request ↔ `ChangeRequest`. `head_sha` stays part of its identity, so a verdict
     binds to a commit, never to a moving head.
   - commit build statuses ↔ `CheckResult`
   - branch restrictions ↔ `ProtectedRef`
   - PR comments ↔ `ForgeComment`; PR approvals ↔ `ForgeReview` (approximate: Bitbucket has
     no review-with-body object; document the loss)
   - releases: Bitbucket has no first-class release object. The verb returns the
     `NotSupported` problem that #332 introduces, never an empty success. Whether
     tags + Downloads should stand in is an open question below.
   - issues: availability of Bitbucket's own issue tracker must be verified. Ticketing's
     sovereign default is Plane (8.b, `doctrines.md:140-142`), and Jira is declared-only.
4. `ForgeSelector` gains `_bitbucket`, and `ADAPTED_PLATFORM_KINDS` gains `"bitbucket"`. The
   existing test that holds `ForgeSelector.kinds` equal to that tuple keeps passing.
5. Nothing becomes a default. With no `[platform]` table the kind stays `forgejo`
   (`config.py:288`).
6. Docs: `docs/configuration.md` `[platform]` rows, `docs/architecture.md` (stop saying it is
   refused), and the adoption guide.

## Acceptance criteria

- [ ] `PlatformConfig(kind="bitbucket")` loads. The "not implemented yet" test is replaced
      by one that asserts the adapter is selected.
- [ ] `BitbucketForge` passes the shared forge-adapter contract suite (the one #332
      establishes) against an in-memory/fixture transport, with no network in CI.
- [ ] Every verb Bitbucket cannot express returns a named `NotSupported` problem, and a
      test asserts each one.
- [ ] `vibey-gh tidy` runs its clean-repo survey against a Bitbucket fixture.
- [ ] An opt-in live test under the tenant's live tests runs only when
      `VIBEY_GH_BITBUCKET_TOKEN` (name configurable) is present, and passes against a real
      repository at least once, with the run recorded as evidence (10.f).
- [ ] vibey-gh's own gates stay green: `python -m pytest -q` with its 100% branch floor,
      black, isort, and mypy.

## Proposed child issues

1. **feat(gh): a Bitbucket transport behind `ForgeTransportInterface`.** Create
   `vibey_gh/bitbucket_transport.py` and its interface, copying `forgejo_transport.py`'s
   shape: host, token from env, JSON GET/POST/PUT, page-following via the `next` link, and
   HTTP error → problem string. Tests in `test/test_bitbucket_transport.py` use a fake
   opener to assert URLs, headers, pagination and error mapping. No adapter yet. (Sized for
   one lane.)
2. **feat(gh): `BitbucketForge` read verbs.** `get_change_request`,
   `open_change_request_heads`, `get_issue_thread` (PR comments), `get_reviews`
   (approvals), `get_check_results` (commit statuses), `get_protected_refs`, and
   `list_artifacts`. Use fixture JSON under `test/fixtures/bitbucket/`. `releases` returns
   `NotSupported`.
3. **feat(gh): `BitbucketForge` write verbs.** `create_comment`, `update_change_request`,
   `merge_change_request` (with the merge strategy mapped), and `set_protected_ref`, with
   `NotSupported` for `create_release`. Fixture tests assert the exact request bodies.
4. **feat(gh)!: `[platform] kind = "bitbucket"` is accepted.** Add it to
   `ADAPTED_PLATFORM_KINDS` and `ForgeSelector`, replace the refusal test, and update
   `docs/configuration.md` and `docs/architecture.md`.
5. **Design needed first — Bitbucket Pipelines equivalents of the managed workflow set.**
   This depends on #138's per-forge template decision. Pipelines has no `workflow_run`
   chaining, so the gate composition needs its own shape.
6. **feat(gh): a Bitbucket reader for `forge-snapshot`.** This comes after #136 S3. It maps
   PRs, comments and statuses into the snapshot's envelope and lists Bitbucket-only
   exclusions.

## Open questions for the operator

1. **Bitbucket Cloud, Bitbucket Data Center (self-managed), or both?** Data Center runs on
   the operator's hardware but is proprietary and licensed. Under 8.a/8.b it is still a
   counterparty. Which does "support" mean?
2. **What does "relays through the sovereign host" (8.b) mean for a Bitbucket-hosted
   repository?** Should Forgejo hold the mirror as the source of truth, with Bitbucket
   receiving pushes and PR status? Or is a direct Bitbucket adapter (like today's GitHub
   one) enough for now?
3. **Releases:** should tags plus the Downloads area stand in for releases, or should the
   release verbs stay `NotSupported` on Bitbucket?
4. **CI parity:** is running vibey-gh's gates as Bitbucket Pipelines in scope (child 5), or
   is the adapter enough?
5. **Jira pairing:** should a Bitbucket adopter get the Jira relay (#85, runbook 01) in the
   same work, or separately?
