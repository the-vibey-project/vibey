Closing as superseded by draft ADR-0046 (two loops). **Nothing from this issue was merged.**

This lane builds the executor for a per-engine service that holds exactly one `binary` (ADR-0044 §13). Sub-doctrine 8.c as ratified by #392 (`doctrines.md:196-234`: exactly two loops, a single instance per model) replaces that shape: in ADR-0046 each run is executed by a loop's **seat host** (§3, "Flow for a BUILD job", step 7), which runs the binaries of its own loop's adapters.

Where the still-useful parts go (ADR-0046's lane list is still to be filed):
- `infrastructure/loop_service/local_run_executor.py` and `result_store.py` keep their names and roles (§10 table, line 304); the seat host drives them.
- The security boundary — only the loop's own adapters' binaries, `args[0]` validated, `cwd` under `[loop_services] root`, environment only from the loop's configuration, never from a message — is ADR-0046 *Security impact* (lines 384–392).
- `<cwd>/.vibey/diagnostics/<run_id>.result.json`, written atomically before the ack, is the "a run" row of ADR-0046 §3's idempotency table (a persisted result is re-sent, never re-run).
- `LocalRun.stop` (inbox stop, grace, then `ProcessReaper.kill_and_reap`) and the control-to-inbox mapping carry over; the inbox and launcher are R20's extracted classes (#367, which ADR-0046 keeps).
- The scripted fake engine written onto `PATH` in a temp directory stays the test pattern.

Evidence: `specs/ADR-two-loops.md` §3, §10 and *Security impact*; `specs/rabbitmq-lanes.md`, lane R21.
