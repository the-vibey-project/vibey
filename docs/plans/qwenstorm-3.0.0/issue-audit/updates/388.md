Part of the **QwenStorm for 3.0.0**. A local sovereign lane (qwenloop until ADR-0046's rename lands) implements this issue; the result is reviewed and verified before it becomes a pull request.

## Why
Sub-doctrine 8.d (`src/vibey_tools/gh/docs/doctrines.md:236-269`) designates **GPT-OSS 20B served by
Ollama** as this era's default model. It is recorded 2026-09-22 with this evidence: on an M5 with
24 GB, one ten-turn agent session ran in 86 s with a 131,072-token context in 13.1 GB, against 215 s
at 32,768 tokens for Qwen2.5-Coder-14B on llama.cpp. #387 made `gpt-oss:20b` qwenloop's
`DEFAULT_ENDPOINT_MODEL` (`src/vibey_runners/qwen/src/qwenloop/domain/config.py:15`; integrated at
`ddf2bf05`).

Sub-doctrine 8.c (`doctrines.md:196-234`, as amended by #392) runs each loop as **a single instance
per model**. ADR-0046 §4 (draft, `specs/ADR-two-loops.md`) adds that a laptop keeps **one model
resident**: a 24 GB machine cannot hold GPT-OSS 20B (13.1 GB) beside qwenloop's managed llama.cpp
server (16 GB).

Yet qwenloop's `BackendSelector.select`
(`src/vibey_runners/qwen/src/qwenloop/application/backend_selection.py:23-46`) picks in this order:
an explicit backend, then a configured endpoint, then vLLM on a large NVIDIA GPU, then its own
managed llama.cpp server. It never chooses a running local Ollama unless one is configured. So on a
Mac the default path starts a 16 GB `llama-server` with Qwen2.5-Coder-14B beside an Ollama that
already serves the default model: two models resident on one machine.

The attach path already exists. `_attach` (`src/vibey_runners/qwen/src/qwenloop/cli/app.py:188-196`)
uses `config.endpoint_url`, which falls back to Ollama's default `http://127.0.0.1:11434/v1`
(`domain/config.py:13`, `:42-45`). Only the choice is missing.

The tenant's `tests/conftest.py:7-22` deliberately keeps a developer's running Ollama out of every
test. So the new probe must be switchable by setting, and injectable at a declared seam. Sub-doctrine
9.b (`doctrines.md:349`) says substitution happens at the declared seam, never by patching an import.

## Required behaviour
1. **Selection.** `BackendSelector.select` gains a keyword input `ollama_available: bool = False`.
   With `requested` AUTO and no endpoint configured, `ollama_available=True` returns
   `BackendChoice(Backend.OPENAI_COMPAT, "a local Ollama is running at 127.0.0.1:11434: attaching to it rather than starting a second model server (sub-doctrine 8.c)")`.
   This rule comes ahead of the vLLM and llama.cpp rules. `BackendSelectorInterface`
   (`application/interfaces/backend_selection_interface.py:13-22`) declares the new keyword.
2. **The probe.** New `class OllamaProbe` in `src/qwenloop/infrastructure/ollama_probe.py`:
   - `__init__(self, *, url: str = "http://127.0.0.1:11434/api/version", timeout_seconds: float = 2.0, opener: Callable[..., Any] = urllib.request.urlopen)`;
   - `available(self) -> bool` performs one GET through `opener(request, timeout=timeout_seconds)`.
     It returns True on a 2xx answer, and False on any `OSError`, `ValueError` or non-2xx response.
     It never raises.

   Its interface `OllamaProbeInterface` goes in `src/qwenloop/infrastructure/interfaces/ollama_probe_interface.py`,
   copying `inference_interface.py`'s style, and is exported from that package's `__init__.py`.
3. **A setting, not a constant (12.c).** `QwenConfig` gains `attach_local_ollama: bool = True`
   (`domain/config.py:20-45`). It is parsed like the other fields (a non-bool is refused naming the
   key) and read from the file key `attach_local_ollama` and from the environment variable
   `QWENLOOP_ATTACH_LOCAL_OLLAMA`, which `SettingsLoader.ENVIRONMENT_KEYS` maps. The loader turns
   `0/1/true/false/yes/no/on/off` into a bool, so add the conversion there or in the parser.
4. **Composition.** `_select(config, *, probe: OllamaProbeInterface | None = None)` and
   `_server_for(config, *, probe: OllamaProbeInterface | None = None)` (`cli/app.py:178-185`, `:207-222`):
   - the probe runs **only** when `config.backend is Backend.AUTO`, `not config.endpoint_configured`
     and `config.attach_local_ollama`;
   - `None` means `OllamaProbe()`;
   - its answer is passed as `ollama_available`.

   Otherwise `ollama_available=False`, and nothing touches the network. When the choice is
   OPENAI_COMPAT, `_server_for` attaches exactly as today, through `_attach(config)`, with
   `config.model` (default `gpt-oss:20b`).
5. **Without a running Ollama, or with `attach_local_ollama = false`,** behaviour is exactly as
   today: the llama.cpp portable profile.
6. **Test isolation.** The tenant's `tests/conftest.py` autouse fixture also does
   `monkeypatch.setenv("QWENLOOP_ATTACH_LOCAL_OLLAMA", "0")`. The environment is a declared seam. This
   keeps a developer's running Ollama out of every test that does not opt in.

## Acceptance criteria
- [ ] Selector: `ollama_available=True` gives OPENAI_COMPAT; `False` keeps today's order; an explicit
      backend and a configured endpoint still win over it.
- [ ] `_select(config, probe=FakeProbe(True))` gives OPENAI_COMPAT. `FakeProbe(False)` gives
      LLAMA_CPP. A configured `base_url` or an explicit backend never calls the probe (the fake
      counts its calls). `attach_local_ollama=False` never calls it either.
- [ ] `OllamaProbe(opener=...)` returns True on 200, and False on 500, on `URLError`, and on a timeout
      raised by the injected opener. It passes `timeout=2.0`.
- [ ] `QWENLOOP_ATTACH_LOCAL_OLLAMA=0` and the file key `attach_local_ollama = false` both turn it
      off. A non-boolean value is refused, naming the key.
- [ ] No test touches the network or patches a module attribute to fake the probe.
- [ ] The qwen tenant's gates pass at its 100% floor.
