# Platform abstraction: one forge protocol, Forgejo as the sovereign default, every other forge a declared adapter

## Summary

vibey-gh must run the same lifecycle on any forge: review at the exact head, gate, merge
train, promote, release, realign, provenance, and rulesets. It does this through one
vibey-owned forge protocol (`ForgeAdapterInterface`) with one adapter per platform.
Self-hosted **Forgejo is the default, always on**. **GitHub is the default *paid* forge.**
GitLab (and Bitbucket, #298) are declared-only. The foundation has landed: neutral nouns,
three adapters, a selector, and a Forgejo default. But only one command (`tidy`) goes
through the adapter today. Everything else still runs `gh`. This issue is the umbrella that
closes when every forge operation goes through the adapter, a real Forgejo instance carries
the full lifecycle, and a fully local reference deployment is documented and proven.

## Why

- **8.b** (`src/vibey_tools/gh/docs/doctrines.md:138-139`): "Forge defaults to self-hosted
  Forgejo, never to a hosted platform. GitHub and GitLab are declared-only."
  `:168-177`: one vibey-owned protocol per surface, naming `ForgeAdapterInterface`
  explicitly. The sovereign adapter "is never turned off and never demoted to a fallback".
  `:188-194` makes **GitHub the default paid forge**. That applies where a human declares a
  paid forge without naming which.
- **8.a** (`doctrines.md:99-118`): the sovereign path is the preference, not the fallback.
  The original ask called Forgejo "mandatory" but GitLab "first-class". 8.a/8.b reverse
  that ordering.
- **10.a** (`:385-388`): the forge is the largest censorable chokepoint, as the original
  text says.
- **12.a** (`:449-453`): the formal core must be re-implementable against any forge.
- **12.c** (`:455`): the platform is declared in the repository, never assumed.
- **Bill of Rights V** (the Right to Leave): no lock-in to one forge.

## What is stale in the original text

1. "GitLab first-class, Forgejo mandatory." 8.b makes Forgejo *the* default and GitLab
   declared-only. GitHub, not GitLab, is the default paid forge.
2. "GitHub behavior byte-for-byte unchanged — the abstraction refactor is provably a no-op
   for existing adopters." vibey-gh's ADR 0002 (proposed,
   `src/vibey_tools/gh/docs/adr/0002-forgejo-is-the-sovereign-default-forge.md`) flips the
   default `[platform] kind` to `forgejo` (`config.py:288`). An adopter without a
   `[platform]` table is therefore no longer on GitHub by default. Per 8.b, a GitHub adopter
   must now declare `kind = "github"`. That is a deliberate break, not a no-op, and it needs
   a migration note.
3. **This repository declares no `[platform]` table** (neither `.vibey-gh.toml` nor
   `src/vibey_tools/gh/.vibey-gh.toml`). The one adapted command, `vibey-gh tidy`, would
   therefore select `ForgejoForge` at `forgejo.local` (`forge_selector.py:83-89`,
   `forgejo_transport.py:29`), while every other command still calls `gh` against GitHub.
   `config.py:283-286` names exactly this as the "half-honoured" state.
4. The original "library layer, in-package, zero runtime dependencies" choice still holds
   (`src/vibey_tools/gh/pyproject.toml:30` `dependencies = []`).

## Scope / Required behaviour

1. Every vibey-gh operation that touches a forge goes through `ForgeAdapterInterface`. No
   module outside the adapters and transports runs `gh`, `glab` or a forge HTTP call
   directly. An import or grep test enforces this.
2. `[platform] kind` defaults to `forgejo` (ADR 0002). `github`, `gitlab` and (with #298)
   `bitbucket` are declared-only. A declared paid forge relays through the sovereign host
   per 8.b.
3. Exact-head semantics survive translation on every adapter. A verdict binds to a SHA,
   never to a change request's moving head. There is one property test per adapter.
4. The managed automation (workflow templates) is rendered per forge from the same
   doctrine-bearing sources: GitHub Actions (today), Forgejo Actions, and GitLab CI.
5. A fully local reference deployment (Forgejo + Ollama with this era's default model
   (8.d) + local-authority + failover + the sovereign review lane) is documented and proven
   end to end with zero cloud.
6. GitHub adopters get a clear migration: declare `[platform] kind = "github"`. `vibey-gh
   check` warns loudly when a repository's origin is on a hosted forge but no `[platform]`
   is declared.

## Original text

Issue #138, "Platform abstraction: one global standard, adapters for every major git platform — GitLab first-class, Forgejo mandatory for fully-local zero-cloud operation", opened by @adammatthewsteinberger on 2026-09-15T10:23:11Z. Body, verbatim:

~~~~markdown
## Ask

Extend vibey-gh beyond GitHub: define **one platform-neutral global standard** for everything the tool does — reviews bound to exact heads, gates, merges, promotions, releases, provenance checks, rulesets, realignment — and convert it to each concrete platform's exact specification through an adapter layer. Major platforms now (**GitLab** is the prime example), and **at least one FOSS platform — Forgejo — is mandatory**, so the entire system can run completely local with zero need for cloud integration at all.

## Shape

- **The global standard**: a platform-neutral operations core. The capability registry (`vibey_gh.surfaces`) already enumerates what the tool does; this issue lifts the *implementations* to the same neutrality — every operation expressed against abstract nouns (change-request, head, check, gate, protected-ref, release, artifact-index) with platform-specific verbs supplied by an adapter.
- **Adapter layer: a library layer, in-package.** Of the three candidates (submodule, microservice, library), the library wins on this repository's own law: zero runtime dependencies is load-bearing, a microservice is a deployment nobody asked for, and a submodule fragments provenance. `[platform] kind = "github" | "gitlab" | "forgejo"` in `.vibey-gh.toml` selects the adapter; everything above the adapter never mentions a platform by name.
- **GitLab adapter**: merge requests ↔ change-requests, pipelines ↔ scans, approvals/required checks ↔ the gate, protected branches ↔ rulesets, releases + package registry ↔ the dual-channel publish. Exact-head semantics must survive translation: a verdict binds to a SHA, never to an MR's moving head.
- **Forgejo adapter (the sovereign rung — mandatory)**: Gitea-compatible API, self-hosted on the operator's own hardware. Paired with `local-authority`, `failover`, and the local review lane, this closes the last loop: **the entire pipeline — hosting included — runs air-gapped on one machine**, answering to no cloud's permission. This is sub-doctrine 10.a applied to the platform itself: the forge is currently the largest censorable chokepoint we have left, and Forgejo removes it.
- **Actions-equivalents**: the rendered-workflow system needs per-platform templates (GitLab CI YAML, Forgejo Actions — near-GitHub syntax by design) generated from the same doctrine-bearing sources, so the prompts, gates, and schedules stay identical in meaning everywhere.

## Acceptance

- The abstract operations layer documented in the architecture map and the paper (translatability, 12.a: the formal core re-implementable against any forge).
- GitLab and Forgejo adapters each drive the full lifecycle on a real repository: review → gate → merge → promote → release → realign, with provenance checks green.
- A documented fully-local reference deployment: Forgejo + ollama + local-authority + failover on one machine, zero cloud, end to end.
- GitHub behavior byte-for-byte unchanged — the abstraction refactor is provably a no-op for existing adopters.

Doctrine: 10.a (censorship resistance — the forge is a chokepoint), 10 (no guarantees — no platform assumed), 12.a (translatability across stacks), doctrine 8 (the local lane, now including the forge itself).
~~~~
