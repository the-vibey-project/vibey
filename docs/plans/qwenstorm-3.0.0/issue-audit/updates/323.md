## Why
`src/vibey/infrastructure/config_loader.py:11-16` says set environment variables beat the file "so
no vibey.toml has to exist at all". But `src/vibey/bootstrap.py:740-749` calls
`load_config_from_path` only when `./vibey.toml` is a file. Without one, `resolved_config` is `None`,
and every surface falls back to its in-memory adapter (`bootstrap.py:751` onwards). The Helm worker
runs in `/work` (`deploy/helm/vibey/templates/worker.yaml:280`) with no vibey.toml. So the
`VIBEY_TRACKER_*` / `VIBEY_DOCS_*` variables that the chart injects (`worker.yaml:120-148`) are ignored.

Also, a malformed vibey.toml is swallowed with `except Exception: pass` (`bootstrap.py:748-749`).
Startup must not block, but the operator must be told.

Two traps the first version of this issue walked into:
- `parse_config` refuses a document with no `[project] name`
  (`src/vibey/domain/config.py:367-370`, `ConfigError("project.name", "missing required field 'name'")`).
  An environment-only load must supply a synthetic project name, the way
  `load_runtime_config_from_path` already does (`config_loader.py:118-122`).
- `build_app` can only be tested today by patching `asyncpg.create_pool`
  (`tests/infrastructure/test_sovereign_surfaces.py:636`, `:703`; `tests/test_bootstrap.py:107`).
  Sub-doctrine 9.b (`src/vibey_tools/gh/docs/doctrines.md:349`) says substitution happens at a declared
  seam, never by patching an import. So this lane puts the decision in a class that tests can call
  directly, and does not add new tests that patch.

## Required behaviour
1. **One overlay step.** Extract the local-engine switch loop in `load_config_from_path`
   (`config_loader.py:85-97`) into a private `_apply_local_switches(data, environ)`. Both loaders
   call it, then `apply_env_overrides(data, environ)`. `load_config_from_path(path, environ=os.environ)`
   gains the keyword. Existing callers are unchanged, and so is its behaviour.
2. **`load_config_from_environment(environ: Mapping[str, str] = os.environ) -> VibeyConfig`**, a
   module function beside `load_config_from_path`. Write this reason at its definition: "Module-level
   beside `load_config_from_path`, which callers already import as a function;
   `StartupConfigResolver` composes the two." It works in four steps:
   - start from `{"project": {"name": "environment"}}`;
   - apply the overlay from (1);
   - call `parse_config`;
   - propagate a `ValueError` or `ConfigError` raised by a bad variable.
3. **`class StartupConfigResolver`** in `config_loader.py`, with
   `__init__(self, *, environ: Mapping[str, str] = os.environ, log: logging.Logger | None = None)`
   (default: `logging.getLogger("vibey.bootstrap")`) and `resolve(self, cwd: Path) -> VibeyConfig | None`:
   - when `cwd / "vibey.toml"` is a file, return `load_config_from_path(it, self._environ)`;
   - when loading that file raises (`OSError`, `ValueError`, `ConfigError`), log one warning naming the
     file and the error, then fall back to the next step;
   - otherwise, return `load_config_from_environment(self._environ)`;
   - if the environment load raises, log one warning naming the variable's error, and return `None`.
     That is today's all-in-memory behaviour, and startup is never blocked.
4. **Bootstrap.** `bootstrap.py:740-749`: when `config` is `None`, set
   `resolved_config = StartupConfigResolver().resolve(Path.cwd())`. An explicitly passed `config=`
   still wins. The bare `except Exception: pass` goes away.
5. A process with neither a file nor variables behaves exactly as today: every surface is in-memory,
   because an environment-only config has no complete surface table.
