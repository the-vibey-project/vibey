Closing as superseded by draft ADR-0046 (two loops). **Nothing from this issue was merged.**

`vibey loop-service --engine ID` starts one service per engine id, and `--prefetch` raises throughput per engine. Sub-doctrine 8.c as ratified by #392 (`doctrines.md:196-234`) allows exactly two loops, a single instance per model, and raises throughput only through the one instance's capacity. ADR-0046 replaces the command with `vibey loop-service --loop <sovereignloop|paidloop>` and keeps `vibey loop submit` (§10, `cli/` row). The per-model instance limit is enforced by the broker through exclusive consumers (§3).

Carried over:
- `bootstrap.build_loop_service` / `build_loop_client`, raising R17's `QueueBackendNotConfigured` without an AMQP URL;
- the SIGTERM handling copied from the worker, drain, then exit 0;
- `vibey loop submit … [--follow] [--timeout]` printing the `RunResult` as one JSON line and exiting with the run's code, or **75** on saturation;
- `ModelResidency` becomes ADR-0046 §4's residency machinery: `ResidencyPolicy`/`ResidencySchedule` (`domain/residency.py`), `resident_schedule.py`, and `model_runtime.py`, which also unloads the old model on a switch (Ollama `keep_alive: 0`) — a behaviour this lane did not have;
- the rule that the loop needs no database (§2, "the loop needs only the broker and the shared volume").

Evidence: `specs/ADR-two-loops.md` §3, §4 (lines 193–222), §10 (lines 298–312). ADR-0046's lanes are still to be filed.
