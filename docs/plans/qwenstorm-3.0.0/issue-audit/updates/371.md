Closing as superseded by draft ADR-0046 (two loops). **Nothing from this issue was merged.**

This client publishes a run straight to routing key `<engine_id>` (one queue per engine, ADR-0044 §13). Under sub-doctrine 8.c as ratified by #392 (`doctrines.md:196-234`: exactly two loops, two queue-borne rotation layers), ADR-0046 §3's BUILD flow is: the caller publishes a `vibey.run.route/1` to `<loop>`, awaits `RunRouted` (bounded by `route_wait_seconds`), then publishes the run request to `<loop>`, and the router forwards it to `<loop>.<seat>`. Pinned runs (DESIGN/DECOMPOSE, `vibey loop submit --engine`) send one message that the router routes itself.

Carried over into ADR-0046's `infrastructure/loop_service/client.py` (§10):
- one exclusive, auto-delete, server-named reply queue per caller process, replies routed by `correlation_id = run_id`, unknown ids dropped;
- `message_id = correlation_id = run_id`, `reply_to`, and **no expiration** on requests;
- `RunTicket` (`accepted`, `progress`, `result`, `latest_result`) and timeouts that return `None`;
- `probe()` (now to `vibey.runs.<loop>.probe`) and `control()` (now keyed `<loop>` or `all`).
New in ADR-0046 and not in this lane: the route request/reply and the `route_id` idempotency key (§3 idempotency table, first row).

Evidence: `specs/ADR-two-loops.md` §3 ("Flow for a BUILD job", lines 169–181) and §10. ADR-0046's lanes are still to be filed.
