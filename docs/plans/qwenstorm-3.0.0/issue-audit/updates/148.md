# Spending, saving and investing: vibey proposes, a human approves every transaction, crypto rails only

## Summary

The ask is to give vibey the ability to spend, save and invest, fully configurable and
generic. Vibey does all the doing, but **every financial transaction must first be approved
by a human**. The original named $BTC, $ETH, $XMR and PayPal, through hardware wallets and
DEXes the operator owns. Two things now bind the design:

- **Sub-doctrine 10.b** (ratified 2026-08-29): anything involving payment or monetary
  exchange uses cryptocurrency, "zero exceptions ever. **No fiat processors, ever.**"
  **PayPal is a fiat processor and is out.**
- **SD-01 §6**: "no irreversible action without explicit human approval". The issue's arc
  (vibey does, a human approves) is exactly that floor.

Nothing is built. The first deliverable is a design decision about **custody**. Does vibey
only ever produce **unsigned** transactions that the operator signs on their own hardware
wallet, or may it hold a key under a cap? Everything downstream depends on that answer.

## Why

- **10.b** (`src/vibey_tools/gh/docs/doctrines.md:390-393`): cryptocurrency only, "the most
  secure, most censorship-resistant, most sanction-proof monetary system in existence at
  that moment in history", with no fiat processors.
- **SD-01 §5–§7** (standing subdoctrine, carried verbatim in CLAUDE.md): the law is a
  floor, there is no irreversible action without explicit human approval, and when in doubt
  vibey stops and asks. Silence from the operator means no.
- **ADR-0009** (human gates are parked jobs): approval is a parked job plus a `human_gate`
  row, never a waiting thread.
- **Non-negotiables:**
  - every job is idempotent under replay, which must be *proven* for irreversible
    transfers
  - the ledger is append-only
  - the `CreditsExhausted` precedent: an invariant enforced at the type, a property test
    and a DB CHECK
- **7.c** (`:82-91`): every proposal, approval, signature, submission and confirmation is a
  ledger event.
- **8.b** (`:147-150`): secrets default to self-hosted OpenBao for any credential that
  vibey must hold. Hardware-wallet keys never leave the device.
- **12.c** (`:455`): chains, wallets, limits and approvers are configuration.
- **10.a** (`:385-388`): censorship resistance.

## Scope / Required behaviour

1. **A transaction proposal** as a domain type: rail, asset, amount, destination, purpose,
   expiry and an idempotency key. It is generic over rails (12.c), with no chain
   hard-coded in the core.
2. **An approval gate whose unapproved state cannot execute.** Executing a proposal
   requires a recorded human approval that references the proposal's digest. This is
   enforced at three layers, as for `CreditsExhausted`: the type, a property test, and a DB
   CHECK constraint.
3. **Custody** (per the operator's decision; default assumed here): vibey never holds a
   spending key. It produces an **unsigned** transaction (for Bitcoin, a PSBT). The operator
   signs it on their hardware wallet, and vibey broadcasts the signed transaction through
   the operator's own node (sovereign; no hosted API by default).
4. **Replay safety:** a proposal is executed at most once. A re-delivered job observes the
   recorded submission and does nothing, as a proof test shows.
5. **Save / invest** as defined by the operator (open question 3). No DEX swap or yield
   action without its own explicit approval per transaction.
6. **Limits:** per-period caps and destination allowlists as configuration. A proposal
   over a cap is refused before it reaches a human.
7. **Legal floor** (SD-01 §5): jurisdictional constraints are an operator decision,
   recorded before any rail goes live.

## Acceptance criteria

- [ ] An ADR and a ratified sub-doctrine (12.b) state the custody model and the approval
      invariant.
- [ ] A test proves no code path executes a proposal without an approval row whose digest
      matches. The DB CHECK is exercised against PostgreSQL.
- [ ] A property test: replaying the execute job any number of times submits at most once.
- [ ] One reference rail end to end on a **test network**: proposal → gate → operator signs
      on a hardware wallet → broadcast → confirmation → ledger. Recorded as evidence.
- [ ] PayPal is absent. A test asserts the rail registry contains no fiat processor.

## Proposed child issues

1. **Design needed first — ADR + sub-doctrine: custody and the approval invariant.** Covers
   operator-signed versus capped hot key, who may approve, and how replay safety is proven
   for irreversible transfers.
2. **feat(domain): `TransactionProposal` and `Approval` value types with the
   cannot-execute-unapproved invariant.** Pure domain, with an interface, property tests in
   `tests/domain/`. No I/O. (Sized for one lane.)
3. **feat(db): proposal and approval tables with a CHECK tying execution to an approval
   digest.** A migration plus integration tests. Persistence goes through `PostgresOrmInterface` (SQLAlchemy), never new raw SQL, per the
   ORM standard now being implemented (storm draft `specs/ADR-orm.md`). The unit tests use
   an in-memory fake so the default test run needs no service
   (`specs/fakes-ci-no-services.md`).
4. **feat(gates): a `transaction_approval` gate kind.** The prompt shows the rail, amount,
   destination and digest, and the answer records the approver. Tests with fakes.
5. **feat(ledger): proposal, approval, submission and confirmation event kinds.**
   Append-only tests.
6. **Design needed first — the Bitcoin reference rail** (PSBT from a watch-only
   descriptor, the operator's own node, testnet first).
7. **Design needed first — Monero and Ethereum rails**, after 6.

## Open questions for the operator

1. **Custody:** vibey never holds a spending key (operator signs every transaction on a
   hardware wallet), or a capped hot key held in OpenBao? The rewrite assumes the former.
2. **Chains under 10.b:** 10.b speaks of "the most secure, most censorship-resistant,
   most sanction-proof monetary system in existence" in the singular. Does it permit BTC,
   ETH and XMR together, or one designated system at a time (like 8.d's designated
   model)?
3. **What do "save" and "invest" mean?** Holding in a cold wallet, DEX swaps, or yield?
   Each needs its own risk statement.
4. **Confirm PayPal is dropped** (10.b), rather than re-framed.
5. **Approvers:** only you, or a named quorum?
6. **Legal and tax:** which jurisdiction's rules apply, and who records compliance before
   a rail goes live (SD-01 §5)?
