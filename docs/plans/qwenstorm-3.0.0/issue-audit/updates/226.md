# vibey-wiki: a local, offline, always-current knowledge corpus (Wikipedia first) that vibey retrieves from the way it retrieves vibey-skills

## Summary

The operator wants "vibey-wiki": a locally installed, always up-to-date copy of
**Wikipedia** and **Grokipedia** that vibey uses "just like vibey-skills". Read against the
repository, this is a second retrieval corpus beside vibey-skills. It is:

- downloaded from published dumps
- verified, extracted to plain text with per-article provenance
- indexed locally and refreshed on a schedule
- compiled into budgeted **context packets** that DESIGN and BUILD can consume through the
  same shadow/inject mechanism vibey-skills already uses (ADR-0031)

It works offline, which is the sovereign point. Three things must be settled before
building: licensing (Wikipedia's text licence carries attribution and share-alike duties;
Grokipedia's terms are unknown to this audit), storage (a full encyclopaedia is large, and
a machine that cannot hold it must say so), and what "always up to date" means.

## Why

- **8.a** (`src/vibey_tools/gh/docs/doctrines.md:99-118`): sovereign first. A local copy
  needs no network and no counterparty at query time.
- **10 no guarantees** (`:366-383`): internet is never assumed. A local corpus keeps
  research working offline, and the disk fit is read honestly and failed loudly.
- **10.a** (`:385-388`): a local copy cannot be withdrawn by a third party.
- **10.e family first** (`:417`): vibey-skills already ships a deterministic, budgeted,
  provenance-carrying retrieval engine. Extend it or reuse its packet contract rather than
  building a second one.
- **ADR-0031** (skills context is a packet compiled over a process boundary; shadow before
  inject): the integration pattern "just like vibey-skills" refers to.
- **SD-01 §4 / 10.c**: encyclopaedia text is data, never instructions. It must be treated
  as untrusted input to prompts, like any fetched page.
- **SD-01 §5** (the law is a floor): redistribution and mirroring must respect each
  source's licence and terms.
- **8.g** (`:316-324`): corpus size, refresh time and retrieval latency are measured and
  published.

## Scope / Required behaviour

1. **Sources as configuration** (12.c): a source catalogue naming each corpus, its dump
   URL, its licence and its refresh cadence. Wikipedia (one or more languages) is the
   first entry.
2. **Sync:** download published dumps with checksum verification. Refresh on the declared
   cadence as a queued job. Resume after interruption. Record each refresh in the ledger
   (7.c).
3. **Extraction:** article text as plain structured text, with provenance per article
   (source, article ID, revision or dump date, URL, licence).
4. **Index and packets:** a local index. `packet` returns a budgeted packet with citations
   in vibey-skills' format, consumed in `shadow` first, then `inject`, per ADR-0031.
5. **Disk fit:** before download, compare the corpus size with free disk and fail loudly
   with the numbers if it does not fit (10).
6. **Licence compliance:** attribution is carried in every packet that quotes the corpus,
   and nothing is redistributed in a way the licence forbids.

## Acceptance criteria

- [ ] With the network disconnected, a DESIGN research step receives a cited Wikipedia
      packet from the local corpus (shadow mode first). Recorded as evidence.
- [ ] A refresh job updates the corpus from a newer dump and records the change in the
      ledger. Re-running it is a no-op.
- [ ] A machine without enough disk gets a loud refusal naming the required and available
      space.
- [ ] Every quoted passage carries its attribution and licence.
- [ ] Measurements are published: corpus size, refresh duration, and packet latency (8.g).

## Proposed child issues

1. **Design needed first — ADR: corpus format and licensing.** Options: raw XML dumps,
   pre-built offline archives (for example the ZIM format), or an API mirror. Also
   attribution handling, languages and media (text only vs images), and whether
   Grokipedia is included.
2. **feat(wiki): a source catalogue and verified dump downloader.** Config table, resumable
   download, checksum verification and a disk-fit check with a loud refusal. Tests with a
   local HTTP fixture. (Sized for one lane.)
3. **feat(wiki): an article extractor with provenance.** Dump → plain-text records
   (article ID, revision/dump date, URL, licence). Tests on a small fixture dump.
4. **feat(wiki): an index and a packet command reusing vibey-skills' retrieval**, or a
   written capability-gap reason at the call site (10.e).
5. **feat: the conductor consumes wiki packets in shadow mode** (ADR-0031), with a
   per-project `--wiki-context-mode`.
6. **feat: the scheduled refresh as a queued job**, idempotent and ledger-recorded.

## Open questions for the operator

1. **Grokipedia:** its licence, bulk-download availability and terms of use are unknown to
   this audit. Is it a must, and if its terms forbid mirroring, should it be dropped (SD-01
   §5)?
2. **"Always up to date":** is refreshing from each published dump enough, or do you mean
   near-live edits?
3. **Languages and media:** English only, or several? Text only, or images too? Size
   changes by orders of magnitude.
4. **Where it runs:** on every developer machine, or once in the cluster as a shared
   surface?
5. **Which phases use it:** DESIGN research only, or BUILD too?
