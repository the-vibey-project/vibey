## Why
ADR-0044 §12 (`docs/architecture/decisions/0044-job-queue-port-and-loop-services.md:343-368`). Today KEDA scales on a PostgreSQL copy of the claim's SELECT arm (`deploy/helm/vibey/templates/keda-scaledobject.yaml:49-68`). `tests/infrastructure/db/test_keda_scaler_query.py` binds that copy to the real claim.

In the RabbitMQ backend the queue holds only due work whose dependencies are met. Its length (ready plus unacknowledged) is therefore claimable work plus in-flight work. That honours ADR-0025's rule against scaling on raw depth, and a pod mid-session is not scaled in under its running job.

A broker cannot know which project is "newest", so the unbound worker mode cannot be followed. The chart must fail loudly and name the fixes, rather than scale on something no worker will claim.

The scaler targets the **worker** Deployment only. Sub-doctrine 8.c (`src/vibey_tools/gh/docs/doctrines.md:196-234`) runs each loop as a single instance per model, and "nothing starts a second instance of a loop to go faster". So KEDA must never target a loop Deployment (#377's routers and seat hosts). This lane pins that with a test.

## Required behaviour
1. **`keda-scaledobject.yaml`**
   - When `queue.backend` is `postgres`, it renders **exactly** today's text.
   - When it is `rabbitmq` and `worker.project` is empty, the render fails with:
     `"keda.enabled with queue.backend=rabbitmq needs worker.project: a broker cannot follow 'the newest project'. Set worker.project, or set queue.backend=postgres."`
   - When it is `rabbitmq` and `worker.project` is set, it renders:
     - a `TriggerAuthentication` `<fullName>-worker-rabbitmq`, whose `secretTargetRef` has parameter `host`. It points at the broker Secret's `keda-host` key (#376), or at `broker.existingSecret` / `broker.existingSecretKedaHostKey`;
     - this trigger:
       ```yaml
       - type: rabbitmq
         metadata:
           protocol: http
           mode: QueueLength
           value: "<worker.parallelism>"
           activationValue: "0"
           queueName: "<broker.prefix>.jobs.<canonical lower-case project uuid>"
           vhostName: "<broker.vhost>"
           excludeUnacknowledged: "false"
         authenticationRef:
           name: <fullName>-worker-rabbitmq
       ```
   - `scaleTargetRef.name` stays `<fullName>-worker` on both branches.
2. **`queueName`** must equal `QueueNames(prefix).project_queue(UUID(worker.project))` (R06, `domain/job_dispatch.py`). The existing helper `vibey.workerProjectHex` (`templates/_helpers.tpl:54-61`) returns 32 hex digits without dashes. So add a `vibey.workerProjectUuid` helper beside it that returns the canonical dashed lower-case form, built from the validated hex (`8-4-4-4-12`).
3. **`render.sh`** (`deploy/helm/golden/render.sh`)
   - The `keda-latest` and `keda-project` profiles (`:88-91`) add `--set queue.backend=postgres`, so their goldens do not change.
   - A new profile:
     `profile keda-rabbitmq --show-only templates/keda-scaledobject.yaml -- --set keda.enabled=true --set queue.backend=rabbitmq --set worker.project="$PROJECT"`.
   - A new `expect_fail NAME ARGS…` function asserts that `helm template` fails, and prints `ok      NAME (fails as expected)`. It is used once, for `--set keda.enabled=true --set queue.backend=rabbitmq`.
