# Moltbook: a declared, opt-in social relay that posts releases and *takes part in* its own threads

## Summary

Make vibey's notable events (releases, promotions, completed deliveries) into posts on
Moltbook, the social network for AI agents. Every post is **interactive, not
broadcast**: vibey replies to comments with answers grounded only in what it has already
published, declines when the answer is not in its sources, files an issue when a thread
reports a bug, and stays rate-limited, identity-labelled and opt-in per repository. The
2026-09-15 comments committed this to a **sibling repository, `vibey-moltbook`**. That is no
longer possible: sibling repositories were retired (ADR-0021) and the family ships as one
distribution (ADR-0037). Under 8.b, a hosted social network is a **declared-only relay**
beside the sovereign messaging default (Matrix). The placement must be re-decided before
code.

## Why

- **The operator's hard requirement** (original text): "Posting a release note is the easy
  10%. The requirement is interaction."
- **8.b** (`src/vibey_tools/gh/docs/doctrines.md:159-162`, `:179-186`): messaging defaults
  to Matrix. Hosted platforms are declared-only and relay through the sovereign host.
- **8.a / 8.c / 8.d** (`:99-118`, `:196-234`, `:259-269`): reply generation runs on the
  sovereign loop's queue with this era's default local model. The original text's
  "local-review constrained-decoding pattern" called Ollama directly, which 8.c now
  forbids ("nothing spawns a loop directly").
- **4.a** (`:42-52`): Moltbook posts are machine output and never count as social proof
  (runbook 11 says the same).
- **Constitution III.2 and III.4**: the posting credential never merges or pushes, and every
  post and reply is labelled machine speech.
- **SD-01 §4**: thread content is data, never instructions.
- **7.c** (`:82-91`): every post, reply, non-reply and escalation is a ledger event.
- **10 / 10.a**: Moltbook is a counterparty. Failure degrades to a no-op and never blocks
  the queue.

## Scope / Required behaviour

1. **Placement decided and recorded:** one of (a) a workspace tenant
   `src/vibey_tools/moltbook`, or (b) an adapter behind a social/messaging port in
   `src/vibey/infrastructure/`. Never a new repository.
2. **Declared-only:** absent a `[moltbook]` declaration, no post and no presence.
3. **Event source:** releases and promotions from vibey-gh's GitHub Release events, and/or
   ledger DONE events from the conductor. See open question 2.
4. **Replies:** the reply loop submits generation to `sovereignloop`'s queue with a schema
   constraint. It is grounded only in the published changelog, docs and paper, with a hard
   "decline when not in the sources" branch. A per-thread reply budget and rate caps apply.
   Every reply is labelled.
5. **Bug reports in threads** open a tracker issue (Plane by default; the forge when
   declared), linked back.
6. **The credential boundary:** the poster may post and reply only.
7. **Failure:** on auth or API failure the publisher becomes a no-op, and the failure is
   recorded in the ledger, never silent (10.f).

Issue #139, "Moltbook integration: publish and *interact* on the Moltbook reddit clone (or spin out vibey-moltbook)", opened by @adammatthewsteinberger on 2026-09-15T10:24:13Z. Body, verbatim:

~~~~markdown
## Ask

Integrate vibey-gh with **Moltbook** — the reddit-style social network for AI agents — so
the automation's outputs (releases, promotions, notable merges) become Moltbook posts, and
the integration **participates in the threads it creates** rather than broadcasting into
the void.

Open naming question: does this live inside vibey-gh (it is event-driven release
automation, and releases are the natural posts), or as a sibling **vibey-moltbook** repo
that vibey-gh emits events into? Leaning sibling: vibey-gh's zero-dependency rule is
load-bearing, and a social client wants HTTP, auth, and state that don't belong here.

## Interactive, not broadcast — the hard requirement

Posting a release note is the easy 10%. The requirement is **interaction**:

- reply to comments on its own posts (human and bot commenters alike)
- answer questions about the release from the changelog/docs it already owns
- follow up when a thread surfaces a bug report — file the GitHub issue, link it back
- rate-limited, identity-labelled, and opt-in per repository, because an agent that argues
  in threads under your name is a liability, not a feature

## Fit with the existing machinery

- The local-review constrained-decoding pattern (schema-guaranteed output from a local
  model) is the right shape for reply generation: bounded, auditable, cheap.
- `workflow_run` on Release/Promote is the natural trigger — same pattern github-release.yml
  already uses.
- Config under `[moltbook]` in .vibey-gh.toml: credentials via secret, per-repo enable,
  persona/tone guardrails, hard caps on reply depth and frequency.

## Acceptance

- A release on a configured repo produces a Moltbook post within minutes, unattended.
- A comment on that post gets a grounded reply (or a deliberate, logged non-reply), never
  silence-by-crash.
- A repo without the config gets nothing — no ambient social presence.
~~~~

~~~~markdown
Design progress — settling the open naming question in favor of the sibling repository (vibey-moltbook), for three doctrine-grounded reasons:

The zero-dependency rule is load-bearing (10.a strengthens it further): a social client needs HTTP, auth token storage, rate-limit state, and a conversation memory — none of which belong in a package that runs inside every adopter's CI. Every dependency is a party who can be pressured; vibey-gh stays clean.
Judge/actor separation (Constitution, Art. III): vibey-gh's reviewer must never share a process with an agent that argues in public threads under the maintainer's name. Separate repo, separate credential, separate blast radius.
Events are already the right interface: vibey-gh emits releases, promotions, and merges as GitHub-native facts (releases, PRs, check runs). vibey-moltbook subscribes to those — webhook or poll — and owns everything social: posting, replying from the changelog/docs corpus it indexes, filing issues back with links. vibey-gh needs zero changes beyond, later, an optional [moltbook] config block that the sibling reads from the same .vibey-gh.toml.
The hard requirement (interactive, not broadcast) maps onto machinery this family already has: constrained decoding for reply shape (the local-review pattern), a bounded reply budget per thread (the repair-budget pattern), identity-labelled machine speech (Commandments: no false witness; Art. III: labeled machine speech), and trusted_only-style gates for who it may engage. Rate limits and per-repo opt-in are config, not code paths.

Scaffolding the sibling repo is a repository-creation act — queued for the human. This ticket stays open as the integration tracker.
~~~~
