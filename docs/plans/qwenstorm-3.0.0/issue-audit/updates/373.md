Closing as superseded by draft ADR-0046 (two loops). **Nothing from this issue was merged.**

`LoopServiceCommandExecutor` here submits a DESIGN/DECOMPOSE run to the named engine's own service. Under sub-doctrine 8.c as ratified by #392 (`doctrines.md:196-234`) that service does not exist; ADR-0046 §3 says instead: "**Pinned runs send one message.** These are DESIGN and DECOMPOSE through the command executor, and `vibey loop submit --engine`. The router routes the run request itself, with the pin, and forwards it." The executor stays a component (`infrastructure/loop_service/command_executor.py`, §10).

Carried over into ADR-0046's command-executor lane:
- it implements `vibey.infrastructure.interfaces.CommandExecutor` and returns `CommandResult(returncode, stdout, stderr)`, so the providers do not change;
- `argv[0]` must be the adapter's binary; `--cwd` is required; `--run-id` becomes the run id;
- saturation raises `EngineQueueSaturated`; capacity detection stays in each provider's own parsing (the executor adds none).
Not carried over: `test_opencodeloop_process_runs_unchanged_over_the_service`. Sub-doctrine 8.b as amended by #392 (`doctrines.md:128-137`) repeals OpenCode, and ADR-0046 §9 retires `opencode` in lane L38, so no new test should pin it.

Also note ADR-0046 §4's flag: the sovereign DESIGN/DECOMPOSE providers call Ollama directly (ADR-0027); routing them through sovereignloop is a follow-up outside ADR-0046's set.

Evidence: `specs/ADR-two-loops.md` §3 (line 181), §4 (line 222), §9, §10. ADR-0046's lanes are still to be filed.
