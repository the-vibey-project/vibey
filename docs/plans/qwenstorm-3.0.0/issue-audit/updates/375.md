Closing as superseded by draft ADR-0046 (two loops). **Nothing from this issue was merged.**

This lane's `ServiceAdapterFactory` builds one `LoopServiceAdapter` per engine id, each talking to that engine's own service. Under sub-doctrine 8.c as ratified by #392 (`doctrines.md:196-234`) the service-mode composition is instead the outer layer (`LoopSelector`, `SelectingLoopProvider`) plus an adapter bound to the routed engine (ADR-0046 §2, §3). ADR-0046 §10 names `infrastructure/engines/adapter_factory.py` as the home of the factory.

Carried over, and to be written into ADR-0046's invocation lane when it is filed:
- both modes stay (§2, "Subprocess invocation (kept, 12.c)"): `subprocess` byte-identical, `service` through the loops; precedence `VIBEY_ENGINE_INVOCATION`, then `[engines] invocation`, then `subprocess`;
- `LocalEngineSettings.adapter(..., factory=...)` in place of the hard-coded `LoopProcessAdapter` (`src/vibey/infrastructure/engines/local_engines.py:143-148`);
- `AppResources.command_executor_for(...)` replacing the four `AsyncSubprocessExecutor()` call sites, which now sit at `src/vibey/cli/main.py:430`, `:457`, `:1578` and `:1617` (the issue cited `:428`, `:455`, `:1580`, `:1619`);
- behaviour 5, the conformance worktree defaulting to `<loop_services.root>/.vibey-conformance` in service mode (near `cli/main.py:1316`). ADR-0046 does not mention it, so it must be carried explicitly.
