# VS Code: an extension that lets a human drive vibey, and (separately) VS Code as the engine that replaces OpenCode

## Summary

The operator asked for "a vscode plugin for vibey". Four days later the ratified canon gave
VS Code two roles:

- **an engine**: "VS Code when its provider is local" inside `sovereignloop`, and "VS Code
  on a paid provider" inside `paidloop`, replacing OpenCode in both
- **the default IDE for paid loops**

Those are different things from a plugin a person installs in their editor. This rewrite
keeps this issue for the **human-facing VS Code extension**, which is the literal ask, and
proposes a **separate issue for the VS Code engine adapter and the OpenCode retirement**,
which the canon now requires. The operator should confirm the split.

## Why

- **The operator's ask** (2026-09-18): "this could use a vscode plugin … make a vscode
  plugin for vibey please."
- **8.b** (`src/vibey_tools/gh/docs/doctrines.md:128-135`): engines default to
  `sovereignloop` … "and **VS Code** when its provider is local". `paidloop`'s adapters
  include "VS Code on a paid provider". "OpenCode is repealed as an engine of either loop;
  VS Code takes its place in both, and the runner that drove OpenCode is retired once the
  VS Code adapter carries its work." `:188-194`: "**VS Code** is the default IDE for paid
  loops."
- **8.h** (`:326-333`): whatever ships must work on Arch Linux and macOS.
- **2.b** (`:30`): installable wherever users already are. For an extension that means the
  editor's marketplace, and for 8.a also a FOSS registry (Open VSX).
- **Bill of Rights I and IX**: a human can understand and drive the system from where they
  already work.
- **Non-negotiable**: never block a worker on a human. An interactive editor used as an
  engine must run unattended, which is the hard design question for the engine half.

## Scope / Required behaviour (this issue: the human-facing extension)

1. A VS Code extension, published to Open VSX (FOSS registry, 8.a) and to Microsoft's
   marketplace (declared), that shows:
   - projects and their phase
   - the queue
   - parked human gates, answerable in the editor (`--defaults`, choices, `--raw` JSON)
   - engine health and budget
   - live log drill-down
2. First slice without any server: shell out to the local `vibey` CLI (`status --json`,
   `answer`). Later slices use the HTTP API/MCP from runbook 12 when it exists.
3. Works identically on Arch Linux and macOS (8.h), against a fully sovereign install (no
   paid engine declared).
4. Nothing in the extension needs an account.

## Acceptance criteria

- [ ] The extension source lives in the repository with its packaging declared (12.c), and
      is built and tested in CI (a new Node lane).
- [ ] On a fresh Arch Linux and a macOS machine: install from Open VSX, open a workspace
      with a vibey project, see its phase, and answer a parked gate. Recorded as evidence.
- [ ] Publishing is automated by the same release machinery as everything else (2.b).
- [ ] An example for every command it exposes (doctrine 3).

For the extension (this issue):

1. **Design needed first — the extension's toolchain and CI lane.** TypeScript + `vsce` /
   `ovsx`, a Node version pin, and where it lives (for example `clients/vscode/`).
   Record the decision (ADR).
2. **feat(vscode): a read-only status view from `vibey status --json`.** A tree view of

   the release workflow (2.b).

## Open questions for the operator

1. **Which did you mean by "vscode plugin"?** (a) an extension a human uses to drive
   vibey, (b) VS Code as an engine (now canon), or (c) both? This rewrite assumes (c),
   split into two issues.
2. **Headless VS Code as an engine:** draft ADR-0046 itself says no evidence yet shows a
   headless, account-free agent session in Code - OSS. If V-VS1 to V-VS5 fail, what
   should replace OpenCode in sovereignloop? Keep the native sovereign agent alone, or
   keep OpenCode (declared) longer?
3. **Registry:** is Open VSX-only acceptable for the extension's sovereign path, with
   Microsoft's marketplace as a declared extra?
4. **Confirm the relayed ruling:** sovereignloop drives Code - OSS (as VSCodium ships it),
   and paidloop drives Microsoft's build. Ratify it with ADR-0046 and a canon
   clarification of 8.b's wording "VS Code"?
