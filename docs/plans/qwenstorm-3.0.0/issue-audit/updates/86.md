# Monetization: usage metering and crypto-settled billing for commercial work, with FOSS unbillable by construction

## Summary

The ask is to make it possible to **charge for usage** of vibey for commercial work, and
**structurally impossible to charge for FOSS work**. The free path must never degrade
relative to paid, and an average developer must be able to run the whole stack free.
Three things have changed since this was filed (2026-08-27):

- **10.b** (ratified 2026-08-29): every payment is cryptocurrency. There are no fiat
  processors, ever.
- **ADR-0037**: the whole tree ships as **one** distribution. The original "a self-hosted
  FOSS deployment contains no billing code path at all — absence, not a disabled flag"
  therefore cannot be met by a module inside `vibey`. The boundary must be re-designed.
- The references to "vibey-gh#134/#135" point at vibey-gh-era issues. #134 here is the
  feasibility engine, and #135 is closed.

The repository has **budget brakes** (what vibey spends on engines) and zero **billing**
(what a customer owes). They share the word "cost" and nothing else.

## Why

- **Bill of Rights IV** (the Right to Full Capability): "Every engineer receives the whole
  tool — free, at full strength, forever. No … capability … is ever degraded to make a
  paid tier look better." This is the operator's doctrine in the original text, already
  ratified.
- **10.b** (`src/vibey_tools/gh/docs/doctrines.md:390-393`): cryptocurrency only. **10.a**
  (`:385-388`): every payment processor is a party who can be pressured.
- **8.a / 8.b** (`:99-194`): a hosted billing SaaS would be a declared-only counterparty.
  The default billing path is self-hosted.
- **12.c** (`:455`): pricing is operator configuration, never code.
- **12.b** (`:435-447`): "FOSS is unbillable" binds future decisions, so it needs a
  ratified sub-doctrine, not only an ADR. The Bill of Rights states the free tier, but not
  the unbillability mechanism.
- **Non-negotiable precedent**: an invariant held at three layers (type, property test, DB
  CHECK), as for `CreditsExhausted`.

## Scope / Required behaviour

1. **FOSS classification** at the project level: auditable (a ledger event with the rule
   that fired), disputable (a human gate), and stored with the project.
2. **FOSS is unbillable by construction:** no billable usage record can be constructed for
   a FOSS-classified project. This is enforced at the type, by a property test and by a DB
   CHECK.
3. **Usage metering** derived from ledger events (per run, per phase, per artifact),
   commercial projects only.
4. **Pricing** in operator configuration (12.c), not in code.
5. **Settlement over the crypto rail** shared with #148 and #88 (10.b). No fiat processor.
6. **The billing boundary:** billing code lives where a FOSS install does not carry it.
   See open question 1.
7. **A capability-parity invariant:** a CI test runs the free configuration and asserts it
   exercises every capability. No capability is gated behind a paid flag.

## Acceptance criteria

- [ ] An ADR and a ratified sub-doctrine state FOSS unbillability and the billing boundary.
- [ ] A property test: for any FOSS project, no billable record can be created. A DB CHECK
      rejects one written directly.
- [ ] The capability-parity test is in CI and green.
- [ ] A commercial project's usage is metered from the ledger and priced from operator
      config, with a test against the in-memory ledger fake.
- [ ] The rail registry contains no fiat processor, as a test proves.

## The doctrine, as enforceable rules

This project is by engineers, for engineers, free for all, and stays that way. Applied:

1. **FOSS work is never billed.** Not discounted — unbillable. Work classified as FOSS
   cannot generate an invoice, by construction.
2. **The free path never degrades relative to paid.** Paid buys tailoring, whitelabeling,
   hosting, and support (per vibey-gh#134/#135) — never capability. Any feature whose
   design withholds engineering capability from the free tier is rejected at review, and a
   CI-checkable invariant should assert the free configuration exercises every capability.
3. **An average developer can run the whole stack for free** and get an autonomous software
   engineer out of it. That is the product; the paid product is fit and convenience around it.

## Mechanics to design

- Usage metering (per run / per phase / per artifact) with FOSS classification at the
  project level, auditable and disputable
- Pricing configuration lives with the operator, not in code
- Clean separation so a self-hosted FOSS deployment contains no billing code path at all —
  absence, not a disabled flag
