Updating vibey's SearXNG to a newer pinned image (`vibey searxng install`, or the editor's Update) now pulls with the runtime it was installed with, trust-checked again, never one found later (podman installed beside Docker Desktop, say), so the image stays in the daemon its container runs in; when that runtime is gone or no longer trusted, the install refuses and says to put it back or to run `vibey searxng uninstall --purge` and then `vibey searxng install`, and `vibey doctor` and `vibey searxng status` now say the same instead of only "is not there". `uninstall` and `--purge` of an earlier pin's install remove its container and image through its recorded runtime. A container runtime writable by its group is now refused, as the docs always said ("writable by anyone" covered only the world bit). In your own Zed `settings.json`, an `agent_servers.vibey` entry whose `args` follow `acp` with anything but `--no-bootstrap` (`["acp", "unload"]`, which would run another command) no longer counts as connected: `vibey connect` rewrites it keeping `--no-bootstrap` alone and your `env`. In a project-scope TOML file, a `[mcp_servers.vibey.*]` sub-table no longer survives a rewrite, and an entry spelt so that the rewrite cannot reach it is refused rather than half written (no such client ships today).
