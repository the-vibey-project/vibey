`vibey acp` is an Agent Client Protocol agent an editor such as Zed launches over stdio, and `vibey connect` now registers it with Zed: `--client zed` (and a plain `vibey connect`) writes `agent_servers.vibey = {"type": "custom", "command": "<this install's vibey>", "args": ["acp"], "env": {}}` into `~/.config/zed/settings.json` on macOS and Linux, keeping every other setting and agent server, with the same atomic, no-wider, never-through-a-link write and `.vibey.bak` backup as every other client; `vibey acp`'s own connect step does the same when `~/.config/zed` exists. Zed keeps comments in its settings, and vibey never rewrites a file it cannot read as strict JSON: such a file is left as it is and refused with the exact snippet to paste, unless it already carries that entry (then it is left alone as connected); the other clients still connect and `vibey connect` exits 1. On Linux the file is `$XDG_CONFIG_HOME/zed/settings.json` when `XDG_CONFIG_HOME` is absolute. An entry that already runs this install's `vibey` with vibey's arguments first counts as connected and its file is never rewritten or reformatted; when the entry must change, only `type`, `command` and vibey's leading `args` change, and, in your own user-level configs, your `env`, other keys and extra flags (`["acp", "--no-bootstrap"]`) are kept, by `vibey connect` and by `vibey acp`'s unattended step alike. A project's file (`.mcp.json`, `.vscode/mcp.json`) is the repository's: there only the exact canonical entry counts as connected, any other `vibey` entry (a planted `env`, `envFile`, key or argument) is replaced whole, and doctor reports it as missing even when the Claude Code plugin is installed. The Python fallback launcher now passes flags after its code through to `vibey mcp` / `vibey acp`. A rewrite now keeps the file's indentation, its non-ASCII text (no `\u00f3` escapes) and a UTF-8 byte-order mark; this applies to every JSON client. A refused client -- a file that is not strict JSON, is nested too deeply to parse, is not UTF-8 or valid TOML, or cannot be read -- no longer stops the whole plan (it exited 2, or crashed, before): it is one `Error:` line printed before any question. Every entry `vibey connect` writes now runs the running install's own `vibey` (the console script beside its Python), never one found on `PATH`, as `vibey acp`'s connect step already did; so an existing entry that runs a `vibey` found on `PATH` (`/opt/homebrew/bin/vibey`, `~/.local/bin/vibey`) is now reported by `vibey doctor` as `WARN <client>:mcp-server missing ... does not carry the entry` and rewritten once by the next `vibey connect`; `--list` and the plan show each client's protocol (`mcp` or `acp`). `vibey connect`, `vibey doctor` (a new `llm-tooling` section, last) and `vibey acp`'s doctor step now report, per detected client, each LLM-facing surface vibey offers it -- the ACP agent entry, the MCP server entry, the `vibey-chat-driver` skill (Claude Code through the `vibey` plugin or `~/.claude/skills`, Codex in `~/.codex/skills`) and the `vibey` plugin from the root marketplace (Claude Code) -- as present (`PASS`), missing (`WARN`, with the exact command or snippet that fixes it) or not applicable (`UNKNOWN`); the section only reads, never a config file that is a symbolic link, never a non-regular file or more than 1 MiB, never raises (a file nested too deeply to parse is reported, a folder that cannot be looked into counts as absent) and never fails doctor. Claude Code's skill also counts in the project's own `.claude/skills`. A finding longer than `[acp] live_message_chars` is cut in the editor saying where to read it whole. `vibey doctor --json` reports these as `checks` named `<client>:<surface>`, with no new key. The editor launches `vibey acp`; on first contact it runs doctor and connect, loads the user-level hub and worker units and keeps them running (ADR-0101); see the new ACP guide.
