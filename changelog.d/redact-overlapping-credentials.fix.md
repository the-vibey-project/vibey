The ledger redactor no longer leaves bytes of a credential behind when credential shapes overlap, and it redacts in time linear in the text. Each pattern used to be substituted in turn, so a shorter shape inside a longer credential was replaced first and the longer pattern could no longer match across the marker: `Bearer sk-AAAAAAAAAAAAAAAA.rest` came out as `Bearer [REDACTED].rest`, and `Bearer AKIA…extra`, a JWT with a fourth segment, a Slack token or JWT with an `sk-` run inside, and a Google key holding an `sk-` run all kept a fragment. A credential glued to the one before it (`sk-…sk-…`, `ghp_…ghp_…`) also kept its whole body, because matching resumed where the previous match ended. The credential patterns are now declared as shapes (`CredentialShape`: a short prefix, then character-class runs) on `SecretTextRedactor`, each matched at every start in the original text through a run index that costs one lookup per segment, and overlapping matches are merged into one `[REDACTED]`. The result no longer depends on the order of the shapes, redacting twice changes nothing, and adversarial strings such as `"xoxb-" * 100000` or `"eyJ" * 100000` redact in a fraction of a second (the old regex scan was already quadratic on the second). Output changes only where matches overlap: such a run now becomes a single `[REDACTED]` (for example `Bearer sk-…` becomes `[REDACTED]`, not `Bearer [REDACTED]`, and a run of overlapping AWS key ids becomes one marker). Text with non-overlapping secrets, and secrets that merely touch, redact exactly as before. Shapes and the run index are configuration (`SecretTextRedactor(shapes, index_factory)`), behind `CredentialShapeInterface`, `TextRunIndexInterface` and `SecretTextRedactorInterface`.
