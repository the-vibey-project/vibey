A BUILD run on `claudeloop` or `claudeloop-local` is now given the loop capability bundle from your own `[loops]` (SP-LOOPS Phase 4, ADR-0103). Before the engine starts, vibey resolves the run's snapshot from the lock, writes its capability document into the run's own snapshot folder, records `LoopCapabilitiesSnapshotted` on the ledger (the digest and counts only) and starts the run with `claudeloop run --capabilities PATH`. claudeloop then loads no user, project or local Claude settings: only the snapshot's plugin folders, exactly the catalog's skills, the run's input folders, the MCP servers from `[loops]` (a local one started through a launcher that keeps only its `env_allow` names, a remote one over streamable HTTP) and the repository's `CLAUDE.md` and `AGENTS.md` as instruction text in the system prompt. Four new person-only `[loops]` keys: `builtin_web` (default `false`), `instruction_files` (default `["CLAUDE.md", "AGENTS.md"]`), `instruction_max_bytes` (default `65536`) and `snapshot_max_age_days` (default `7`). **Behaviour change:** vibey no longer passes `--web-search` or `--deep-research` to claudeloop, and Claude Code's own `WebSearch` and `WebFetch` are off in a BUILD run unless you set `[loops] builtin_web = true` (never on `claudeloop-local`); `vibey loops` now reports claudeloop's `web_search` as `false` until every loop gets `vibey_search` (SP-LOOPS Phase 6). DESIGN's bounded research still asks for web search. A snapshot that cannot be resolved parks the job on a `loop_capabilities_unresolved` gate, and the run never starts without it. The run's snapshot folder is removed when the run ends, and a starting `vibey worker` sweeps the ones a crashed worker left.
