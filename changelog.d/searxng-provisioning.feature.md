vibey now installs and runs the local SearXNG its search asks first (ADR-0102). `vibey acp`'s bootstrap gains a fifth step, after PostgreSQL, under `[acp] searxng = "ask" | "never"` (default `ask`; a project's `vibey.toml` may only say `never`) and `auto_services`: once per process, never in `observe`, and only when your environment names no SearXNG of your own (`VIBEY_SEARXNG_URL`), none already answers and vibey installed none before, the editor is asked "Download and run SearXNG (searxng/searxng@sha256:...) in a container on 127.0.0.1:28180?" and only **Install SearXNG** installs. It uses your own `podman` (preferred) or `docker` and never installs one (with neither, it says how to get one, once); it pulls one image pinned by digest (`docker.io/searxng/searxng@sha256:fc1d81d7e9d0...`, refreshed by a reviewed change with `scripts/searxng_image_digest.py`), writes `settings.yml` and `provision.json` (0600, atomic, never through a link) in `<your configuration folder>/searxng/`, writes and loads the user-level unit `<label_prefix>.searxng` like the hub's (restarted by the keep-alive, loaded again by step 3 at each session start), and waits until it answers as vibey's own. The container runs read-only, with every capability dropped, no new privileges, a process and memory limit, as your own user, published on 127.0.0.1 only, never privileged, on the host network or with a home folder, and `vibey searxng serve` (what the unit runs) never pulls. New command group `vibey searxng`: `install [--yes]` (asks first), `status`, `uninstall [--purge]`. `vibey acp unload` now also removes the SearXNG container. Search now finds vibey's SearXNG from your own record when your environment sets neither `VIBEY_SEARXNG_URL` nor `VIBEY_SEARXNG_INSTANCE`. `vibey doctor` gains a `searxng` line after `web-search-backup`; the existing lines and `--json` keys are unchanged. Nothing was run against a real container in this change: ADR-0102 lists the flags that still need that check.
