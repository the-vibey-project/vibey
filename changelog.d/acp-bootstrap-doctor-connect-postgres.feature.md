`vibey acp` sets the computer up when an editor first connects (`[acp] auto_bootstrap`). After `session/new` (or a load or resume) has answered -- never before -- it runs `vibey doctor`'s local sections as a tool call, one update per finished section, and, with `[acp] auto_connect`, registers `vibey mcp` with each user-level client whose config folder already exists under your home folder (never a project file, never a folder it would create, never a config whose real path is outside home; backups kept with the original's permissions; one broken client a `WARN`, tried again next time; a client installed later is connected too). Inside the first prompt of a `drive` session it offers a missing PostgreSQL as a permission request: only "Install PostgreSQL" installs, with the same fixed commands as `vibey doctor --install-postgres`, stdin closed, output captured, a minimal environment, each command in a process group of its own bounded by the new `[acp] install_timeout_seconds` (default 1800; past it the group gets SIGTERM, then SIGKILL, and one that cannot be stopped is reported as possibly still running), and `sudo -n` -- vibey never asks for or types a password, and says when to run the install yourself. "Not now", a timeout, a cancel or `observe` install nothing; once asked, the tool call is closed and one message says the hub runs degraded. A cancel during an install you allowed leaves it running, closes the tool call saying so, and reports how it ended. A second editor window leaves these steps to the first (`<state_dir>/acp-bootstrap.lock`, held until an allowed install has ended). `vibey doctor`'s sections are now doctor probes both share; its output, text and `--json`, is unchanged. A failed hub read no longer runs `vibey hub start` where it stands: `vibey acp` tries at most once per `[acp] hub_start_seconds` (new, default 60) on a thread of its own, says at once that the hub is away, and its `vibey hub start` child (as `vibey mcp`'s) no longer inherits the protocol's stdin.
