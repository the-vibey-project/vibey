`vibey acp` now keeps vibey running for the editor (ADR-0101). With `[acp] auto_bootstrap` and `[acp] auto_services` on (the defaults), its bootstrap writes a user-level unit for each of `[acp] services` -- `<[supervisor] label_prefix>.hub` runs `vibey serve`, `<label_prefix>.worker` runs `vibey worker --all-projects`, both through `vibey supervisor exec --env-file` so no secret is in a unit -- and loads it with `launchctl bootstrap gui/<uid>` or `systemctl --user enable --now`: never a system unit, never `sudo`, never a unit already loaded. Units restart `always` (`[acp] restart`), throttled by `[supervisor] restart_seconds` and, on systemd, the new `[supervisor] start_limit_interval_seconds` (default 600) and `start_limit_burst` (default 5). A unit you edited is kept as it is and neither loaded nor restarted; a hub you started yourself is left running and taken over only once it exits. The first load names each label and the exact `launchctl bootout` / `systemctl --user disable --now` commands that unload them. A keep-alive probes at every prompt and every `[acp] probe_seconds`, restarts only vibey's own units, under the bootstrap lock and after probing again (two windows restart a dead hub once), at most once per period per unit, and says one message per change of state. While the hub is a unit, a hub read that finds no hub restarts the unit instead of starting a second hub. With no service manager reachable (over SSH, or no `systemctl --user`), `vibey hub start` runs once and that is said. `vibey supervisor install` renders and prints exactly what it did; it now writes each unit atomically and refuses to write one through a symbolic link (exit 1), and every unit value carrying a control character is refused (exit 78) while `$` in `ExecStart` is escaped.
