`vibey acp` now keeps vibey running for the editor (ADR-0101). With `[acp] auto_bootstrap` and `[acp] auto_services` on (the defaults) in your own `vibey.toml` -- in your configuration folder (`~/Library/Application Support/vibey/` on macOS, `$XDG_CONFIG_HOME/vibey/` elsewhere); a project's `vibey.toml` can only turn things off or narrow them, and its `[supervisor]` and `[hub]` are never read here -- the bootstrap writes a user-level unit for each of `[acp] services` and loads it with `launchctl bootstrap gui/<uid>` or `systemctl --user enable --now`: never a system unit, never `sudo`, never as root, never a unit already loaded. `<label_prefix>.hub` runs `vibey serve` in your configuration folder; `<label_prefix>.worker` runs `vibey worker --all-projects` and is loaded only once the environment file sets `VIBEY_PG_URL`. Units run the running install's own `vibey` with a fixed PATH, carry no secret, and restart `always` (`[acp] restart`), throttled by `[supervisor] restart_seconds` and, on systemd, the new `[supervisor] start_limit_interval_seconds` (600) and `start_limit_burst` (5). vibey records what it wrote (`<[hub] state_dir>/acp-units.json`): a unit you edited is kept as it is and neither loaded nor restarted, and vibey's own older rendering is replaced. A hub you started yourself is left running and taken over once it exits. The first load names each label and how to stop them: the new `vibey acp unload` unloads them in your own domain and deletes only the unit files still as vibey wrote them. A keep-alive probes at every prompt (bounded by the new `[acp] prompt_probe_seconds`, 10) and every `[acp] probe_seconds`; it is the only thing that restarts the hub's unit, only vibey's own units, only when definitely down, under the bootstrap lock after probing again, at most once per period, holding the lock until the hub answers, so two windows restart it once; notices are damped by the new `[acp] notice_interval_seconds` (3600). Probing the hub never starts it; until the services step has ended a read starts no hub, and after it, when no unit of the hub is vibey's, a read that finds none runs `vibey hub start` in your configuration folder. The service-manager runner allows exactly the commands vibey issues, argv for argv. `vibey supervisor install` renders and prints what it did; it now writes each unit atomically and refuses one that is a symbolic link (exit 1), every unit value carrying a control character is refused (exit 78), and `$` in `ExecStart` is escaped. Not yet run against a real `launchctl` or `systemctl`.
