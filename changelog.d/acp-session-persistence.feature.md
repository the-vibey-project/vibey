`vibey acp`: sessions are kept and can be loaded, resumed, listed and closed. The hub keeps each session's history (migration 0023: `acp_session` and `acp_session_event`, append-only by the ledger's own trigger, `SELECT` and `INSERT` only for the application role) on four new routes under `/api/v1/acp/sessions`, reading or writing only the creating principal's sessions: creating a session and appending to it need the new `acp_sessions` scope (a write, so `view` alone never makes the hub keep anything), listing and reading need `view`; `acp_sessions` joins the default `[hub] agent_scopes` and is never a paired device's unless the host offers it. The hub keeps at most `[acp] sessions_max` (1000) sessions per principal and `[acp] session_events_max` (100000) events per session, refusing more with 507 (E0087) and never dropping or changing what it kept. Without the grant, `vibey acp` keeps each session in its window only and says so once; observe sessions keep their record as drive ones do; `vibey acp` writes through them as the agent principal, behind each turn and in order, resending from where a failed send stopped and holding at most `[acp] pending_events_max` events. What is kept is what a turn showed (your messages, vibey's replies, tool calls and their outcomes), the title, mode switches, the project followed and the close; live ledger messages are not, and a tool call's input is not. `session/load` replays the history before it answers, every stored event rebuilt from checked fields with its text shown by the same plain-text rule as live hub text, never as a command, a permission request or a gate; `session/resume` restores mode and project without replaying. Both resend the `/` commands, follow the project, and keep a session that is still open as it is. A session is found only by its UUID for the folder it was started in, and any other answers `RESOURCE_NOT_FOUND` the same way. `session/list` pages newest first with a cursor. `session/close` cancels a running turn, withdraws its permission requests, stops its live feed and records the close; a later prompt finds no session. A session is kept from its first prompt, so unused `session/new` calls spend no slot; load replays at most `[acp] replay_events_max` (2000) of the newest events and says once when older ones were skipped, reading only a summary of the rest; loads, resumes and closes of one session run one at a time; the hub reads only the two cap keys from `[acp]`, refuses a session folder with characters that are not printable, and checks its caps without counting a log; what the hub's rate limit still holds back when the connection ends is waited for within `[acp] probe_seconds` and said if it stays unsent. New errors E0084 to E0088.
