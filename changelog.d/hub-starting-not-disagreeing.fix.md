`vibey hub status`, `stop` and `start` no longer say "the two disagree" while a hub is starting over an earlier hub's stale record (it holds its lock but has not replaced the record yet): `status` says a hub is starting (exit 3), `stop` signals nothing and says to run it again once the hub is up (exit 1), and `start` waits for that hub instead of launching a second one, so two UIs starting the hub at once both report it. A hub that exits cleanly now empties the process id in `serve.lock` before letting go, so the next hub is never mistaken for it in the instant before it writes its own, and a hub whose start coincides with another command's look at the lock now tries again for a moment instead of exiting as if a hub already ran. `vibey hub pair`, `devices` and `revoke` now say "hub record unreadable" in one line (exit 2) for a malformed runtime record, instead of a traceback.
